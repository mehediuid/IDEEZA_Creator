# Features — other editor modules (Code, 3D, Preview, Wiring, Add Brief)

Part of the feature inventory ([index](README.md)). Moved verbatim from `CLAUDE.md` §5 on 2026-09-29. Keep it current: [AGENTS.md › Keeping docs current](../../../AGENTS.md#keeping-docs-current-required).

## Other editor modules
- **The editor opens a product** (`/project/<slug>/products/<productId>/<step>`, step `pcb · code · 3d · assembly · wiring · preview`; `manual/project-workspace.tsx`): the gate resolves the project, refuses a locked (sold-in-full) one, and an unknown product shows "This product isn't in {project}" rather than another product's board. The Brief stays project-level at `/project/<slug>/brief` (no product route). The legacy `/project/<slug>/<step>` and flat routes redirect to the product the project last opened (`resumeProductOf`, `lib/manual/editor-scope.ts`).
- **Every editor document is per product**: the PCB store (`lib/pcb/store.tsx`, `setDocScope`, `releaseScope`, `usePcbDocScope`) holds no board until a route names a scope, then loads and autosaves `ideeza:pcb:doc:<projectId>:<productId>`; wiring, assembly, the 3D scene, Code files and Preview keep their own scoped keys (`editor-scope.ts`, list in [pcb-architecture.md](../pcb-architecture.md#persisted-state-project-pages-market-wallet-video)). Switching product remounts every editor. A first-row product may read the project's legacy document while it is still the maker's own.
- **A built product's editors open filled from its build** (BUILDLOAD, see [platform-and-projects.md](platform-and-projects.md) › BUILDLOAD): an import banner says what arrived, and a "Bring it in" banner offers the rest, one at a time.
- **Code** (`components/code`): Monaco `dev-editor` + **Blockly** visual editor, AI chat side-panel, code rail/menu, editor switch.
- **3D Module** (`components/3d`): `model-viewer`, **AI generate modal**, sketch mode, three.js canvas, floating tools + left panel + menu bar.
- **Product Preview** (`components/preview`): three.js product assembly — instances, **mate panel**, viewport, toolbar, its own right-click menu.
- **Wiring** (`components/wiring`): wiring canvas + component library + right panel + menu.
- **Add Brief** (`components/brief`): a wizard whose steps depend on the intent (`stepsFor(intent)` in `lib/brief/types.ts`, steps named `BriefStepId` rather than numbered) — **sell** runs idea → preview → form → success, because the clip is part of the listing and is wanted before the money; **give / save** run idea → form → preview → success, the clip last, because it is optional for them and asking for a render before they have said what they are doing with the design is asking for work nobody may look at. **Every intent gets the step**: it used to appear for give/save only when *Share to Innovations* was ticked, which made the media step read as missing — a maker who wanted a clip for a private build had no way to ask for one. Skipping is a **card on the step** now rather than the absence of the step: **Add later** is selectable for a give or a save, and locked only where a clip is really required — a listing (*A listing needs a preview clip*) or anything being posted to Innovations (*An Innovations post needs a preview clip*), since the feed shows video cards. Verified in a browser: with *Share to Innovations* off the Skip card reads **Available**, with it on the same card reads **Locked**. One `commit()` mints and finishes, called from whichever step is last, so the form's CTA reads *Continue to video ›* when a preview follows it and pays when it doesn't. The rail lists the live sequence (**Idea · Preview · Ready to sell / Give to community / Save as Private · Done**, answered steps ticked and clickable to go back) above the editor's module rail. A draft stored when steps were 1–4 still opens on the step it reached (`normalizeStep`). With review + regenerate confirms. Every step renders in the shared **`BriefCard`** frame (surface card, `--radius-2xl`, `--elevation-1`, a "← Back" link above it). **The wizard has two homes** (`BriefApp({ buildId })`): the project's own Brief at `/project/<slug>/brief`, in the editor chrome (top bar · step rail · module rail), and — new — **a finished build's Brief at `/build/<id>/brief`**, in the dashboard shell the review surface already uses (global sidebar, "← Back" to `/build/<id>` over one card, **no module rail and no step rail**, per the design). Build mode exists because there is no project yet: **the draft is keyed by the build** (`ideeza:brief:draft:build:<id>`, via `briefDraftKey`/`buildDraftScope`) until Step 1 attaches it, when it **migrates onto the project's own key** and the wizard carries on in place on that draft — so `/project/<slug>/brief` opens exactly where the build left off. Step 1's examples are hardware (*Smart plant waterer*, *Garden sensors* — they were *Discord Bot* and *Modern Battle Tank*), and it is headed **Add a brief** on a build (the idea has been built — *What's your idea?* asked for one) and arrives **prefilled from the build, including the project it was always for** — the create flow already asked *what should the project be called?* at the setup question, so opening this step with an empty chooser asked the maker the same thing a second time and threw their first answer away. The build carries that decision (`projectChoiceId` / `projectChoiceName` on the job, from the `SetupAnswer`), and the step **reads it back rather than asking it again** — one `PROJECT` row naming it (*Drone · New project · created when you continue*, or *Existing project · already has N products*) with **Change** beside it, the same shape the setup card in the chat uses for an answered question. Prefilling the chooser was not enough: a dropdown reading *+ Create new project* over a *NEW PROJECT DETAILS* panel repeating the name put the project on screen twice, as two controls, both asking. **A system is not offered a move it cannot make**: §4.4.8 keeps a build's products in one project, which is why the setup question asks a multi-product build only for a name and shows it no chooser — so this row offers **Rename**, not *Change*, and opening it reveals the name and description alone. A single-product build, which really may join a project that exists, keeps **Change** and the full chooser. Either way everything is preserved, because an answer you cannot revise is a trap rather than an answer. One line is the model's **description**, not `summary` — that is the parts line, and it was answering *what does it do?* with *ATmega328P · GPS Receiver · IMU · ESC · LiPo Battery* (`BuildJob.description` and `BuildProduct.description` carry it now, from `ConceptSummary`). Product name ← `job.title`, and the concept prompt becomes the project's description when the maker writes none. **Every product the build made is shown and saved**, not just the first: under the two fields, an **Also in this project** list names each companion with its own AI description **and an Edit beside it** — the model's naming is a good first draft and nothing more, so a name read back wrong is fixable here, beside the one the maker is already editing, rather than after the project exists. Edit opens that row into the same two fields the headline product has, with Save and Cancel; Save writes to the draft, so it survives a reload and a step back. **The attachment happens once**: `buildId` outlives it — it is in the URL — so the hand-off branch used to swallow every later press, and stepping back to the idea left Continue doing nothing at all (it re-ran the hand-off into a project the build was already in, `seedDraft` correctly refused because that project's draft now held work, and the step was never written). It runs only while `job.projectId` is not the target; after that Continue is the ordinary advance. The **count** of products always comes from the job, the one thing that knows how many this build made, with the maker's edits laid over it — reading the list straight off the draft wrote a one-product project over a three-product one. And `seedDraft` carries `otherProducts` across the scope change, or a step back re-hydrated on a draft that had never heard of them and the renames went with it. Attaching writes the whole list onto the project (`ManualProject.products`, the headline product's own edits winning for the first row) while `productName`/`description` stay the headline, so every surface reading those is unchanged. A build with no such answer — one booked before this existed — still starts **unanswered**: it belongs to no project until this step, so `""` is a real stored answer that survives a reload (`normalizeBrief` keeps it; `withDefaultProjectChoice` still resolves it to the project you are standing in, in project mode). Attaching is what **selects** the project (`setBuildProject` + `selectProject` + the product name written onto it, `buildId` only on a project this build just made): the one deliberate act, never a side effect of a create. A target that **already holds a brief in progress** keeps it — the build attaches all the same, and the three Step 1 answers (product name · one-liner · intent) **fill that brief's blanks and nothing else**: a field it has already answered is its own and is never written over, and a carried product name is written onto the project record too, since the brief takes its product name from there. The build's draft is cleared only after that carry, so nothing the maker typed disappears unexplained. The notice names exactly which answers travelled — or says plainly that none did, when that brief already answers all of it — and warns when the brief it landed on is **already minted**, because the wizard then opens on that listing rather than on a form; its wording is build-mode's own (the build *joined* the project — nothing is "opened", the same shell re-hydrates in place). The mint closes out **the project the brief belongs to** (`scopeProjectId` — status → Completed, the flow's `brief` step marked, and the name the form and the success card print), never whichever project the editor happens to have selected: a build's brief keeps running on its own project long after My projects has opened another. Its switches are 40×24 targets with an off track in `--color-border-strong` (the raised-surface grey was all but invisible on white), its Back link and *Help me write it* are 32 px tall, and the regenerate flow's toggle is a real `role="switch"` button — it was a `<span onClick>` no keyboard could reach. *Saved as you go* sits under the card at reading contrast — it was a fixed bottom-right note at 60% opacity (2.8:1), where the render toast now lives. The step body is held back until that scope's draft is in hand, so the *New project details* panel can't flash before hydration answers the chooser, and a stored draft's chooser answer is taken at its word — "+ Create new project" with the name cleared out again stays that answer on the next reload instead of reverting to unanswered. Hydration and persistence are keyed by that scope, and the persist effect waits for the scope it loaded (`hydratedScope`), which is what stops a scope change writing the previous answers over the target's draft. **Step 1 chooses the project it attaches to** (`SelectMenu`: `+ Create new project`, then an `EXISTING PROJECTS` section of every `ManualProject`, Draft-suffixed): picking **new** opens an inset *New project details* panel (name + description) and Continue really creates that project, names its product and **navigates into it** (`/project/<slug>/brief` — the URL is what says which project the editor is in, so the draft is seeded there first and Back → Continue attaches to the same project instead of making a second one); picking an **existing** one says so in the hint and a callout that counts what it already holds (`1 + its builds`). The three intent cards carry their real requirement — **Wallet + identity check** · **Wallet needed · no KYC** · **No wallet · no KYC** — and Continue is disabled until the project, product name, one-liner and intent are filled, naming the first missing one in its tooltip. At phone width the intent cards (and Step 2's media cards) stack — three across, they cut the requirement chips off mid-word — and nothing inside the Brief's card is a card of its own: the *Adding to …* note is a tint without a border and *Also in this project* is a list between hairlines. **Step 2 picks the preview in the same frame**: each media card is a header band stating what it costs you — AR **App coming soon** (`--color-bg-warning-subtle` — the phone app isn't released, and a green *Available* sat over a dead end) · AI **Recommended** (the brand's quiet tint — it was the gradient slab, which spent the accent on a recommendation and failed contrast in dark) · Skip **Locked** for Sell/Give (`aria-disabled` + the reason, *A listing needs a preview clip*) — and **AR is now offered to every intent** (`goToStep2` no longer snaps Sell/Give to AI; only Skip stays locked). Under them, the video prompt (`What should the video show?`, with a **Help me write it** link when the parent passes a handler) **arrives drafted** from the product name and one-liner through `videoScenePrompt` and stays editable — there used to be three ways to fill this one field (typing, an *Auto Generate Video* toggle and Prompt Help, the toggle and Prompt Help's fallback writing the same sentence), and now there is the draft and one helper. The audio field's **Auto Generate Audio** row sits below it the same way, quality is a two-tab segmented control (**Low · 480p · 10 sec** / **High · 720p · 10 sec**) beside the *Full video is 10s* note, and the storyboard button is a full-width **outline** reading **Generate storyboard** (**Regenerate storyboard** once one exists), disabled with *Type a prompt first* until there is a prompt. Once a storyboard exists the scenes list in `--color-bg-subtle` rows with the time range in the brand ink (speech placeholder *No Speech in this scene…*), a blue callout says **Click Continue to start rendering your 10s video** / *You will see progress right here. The render keeps running if you leave.*, and the parallel-work line shows from that moment rather than only after the render starts; the render card adds *You can leave — the render keeps running and the project goes live once it is done.*
- **Picking AR opens a real hand-off, not a promise** (`brief/ar-record-panel.tsx`) — Step 2's AR branch used to be a placeholder card saying the QR would be at *the next step*, and Continue carried on to mint with no footage. The panel now prints the code itself: **Record on your phone** · *Scan the code with your phone camera to open the IDEEZA app.* with a **Waiting for phone** chip (warning tokens, a pulsing dot that holds still under `prefers-reduced-motion`), a **200 px QR encoded here and now** by `lib/brief/qr.ts` from `${origin}/brief/ar/<projectId>` — verified by screenshotting the rendered `<svg>` and decoding it back to that exact URL with Chrome's `BarcodeDetector`. The quiet zone is empty coordinate space in the returned path, so the plate paints a light rect across the whole viewBox and keeps dark-on-light in **both themes** (a theme-flipped code is an unscannable code). Beside it, **HOW IT WORKS** numbers the three real steps, and the footer offers the way out — **No phone nearby?** · **Switch to AI instead**, which flips the card to AI. `BriefState` gained **`arClip`** (`{url, receivedAt} | null`, sanitized by `normalizeBrief`) and Continue is shut until one arrives (*The clip hasn't arrived yet*, footer: *Waiting for the clip from your phone.*; a Save brief's way out is the **Skip card** above, which is selectable for that intent). Nothing in the browser writes `arClip` — the phone app isn't released — and the note under the code says exactly that rather than faking an arrival.
- **Step 3 — “Ready to sell” is the real listing form** (its *Video is ready* strip and every other Brief surface read semantic tokens — `--color-bg-success-subtle`, `--color-text-brand`, `--color-bg-brand`, elevation tokens — where they carried raw palette steps and hand-mixed `rgba` that stayed light in dark mode; the one deliberate exception is the video poster art, which is imagery; the Brief's fields show their placeholders in `--color-input-placeholder` instead of the browser's 2.5:1 grey) (the product card's thumbnail is the build's own concept image where there is one — it was a violet gradient —; **Pay** is the app's standard primary button, `radius-lg` and no glow of its own; the price hints read *0.00* rather than a *32* that looked like a value already entered; the labels are plain text, not caps) (`brief/step-3-mint.tsx` `SellFields`, SI06) — inside the shared `BriefCard`, a product card whose thumbnail opens the preview (the existing `ReviewModal`, and the play glyph appears only when there *is* something to watch — an AR clip or a done render — so a poster never offers a player with nothing behind it) over the project → product → one-liner. Then the fields in listing order, each a `SelectMenu`/input with its label above: **Blockchain Mint** (the two testnets — switching chain resets the token to that chain's first and clears the collection, since neither belongs to the other chain) · **Choose collection** (the wallet's own per-chain rows from `lib/brief/wallet.ts` `readCollections`, read once in a lazy initializer, so the seeding write happens once per mount rather than on every render, plus a **+ New collection…** row that names one inline and really writes it through `addCollection`) · **Listing type** — then **Buy now**'s Token + Price, or **Auction**'s **Minimum bidding price** (token + amount) · **Auction Buy Now Price** · **Expired Date** (`datetime-local` with its own calendar button calling `showPicker()`) — and **Royalties (%)**, which can now be emptied, so its placeholder and its own missing-field reason are real rather than a value you can never clear. Four confirms follow in the brief's order (**Instant Mint (Gas fee Applicable)** · the gas confirm · the ownership confirm · **Share to Innovations**, which reveals the **story panel**: *Write your story*, a 500-char textarea and a live `n/500` counter). The **cost card is computed, not drawn** — mint fee 4 IDZ · `Listing (Buy now)` / `Listing (Auction)` at the price (an auction's is its opening bid) · the `estimateGas` row with its muted ≈ $ · **Total to pay now** from `formatTotal` — under a footnote saying the rates are fixed references and that IDZ is IDEEZA's token, paid from the wallet and separate from build credits, and a blue **“Nothing is charged until you approve in your wallet”** callout. The full-width **Pay 4 IDZ and mint** (wallet glyph) is shut until the form is answered, and its tooltip *and* its `aria-describedby` line name the **first** missing field read top-down (chain · collection · listing · price / min bid / expiry · royalties · the gas and owner confirms), with the video-ready note returning once nothing is missing. The confirms are real checkboxes now (an `<input type="checkbox">` under the drawn box), so Tab and Space reach them — they were a mouse-only `<span onClick>`. The auction is checked for the two ways it could be listed and never sell: an **expiry in the past** (the `datetime-local` also carries `min` = now, and the clock is read through `useSyncExternalStore` so an expiry that passes while the form is open really goes stale) and a **minimum bid above the buy-now price** — each its own rung in the ladder. An amount field keeps digits and **one** decimal point, so `1.2.3` can no longer read as a price and parse as `NaN`; the auction's token select carries its own **Token** label, like the Buy-now row's, instead of announcing as its value; the cost card's rule is `--color-border-strong`, since `--color-border-subtle` *is* that card's ground in light theme; and the inline **+ New collection…** namer can be backed out of (Escape or Cancel), which it could not before. **Royalties keeps what you type** — `BriefState.royalties` is text, the field keeps digits and one decimal place, and the CTA states the rule (*Royalties must be between 2 and 10%.*) instead of clamping every keystroke, which used to turn a typed `10` into `20` and put `2.5%` out of reach; hint, placeholder and validation read one range from `ROYALTY_MIN`/`ROYALTY_MAX`, and a stored numeric draft migrates. **The cost card names the chain that was picked** — *Network fee (Base Sepolia)* / *(Mumbai)* — and quotes the fee in that chain's own coin with *test ETH — no real cost* rather than a dollar figure for a faucet coin. **Regenerate opens the preview step by name**, so a give or save posting to Innovations (where the preview follows the form) no longer lands back on the idea. *(Removed: the **Instant Mint** checkbox and, with it, `instantMint` · `blockchainMint` · `confirmGasFees` — every one a control or flag nothing read.)*
- **“Give to community” and “Save as Private” are the same frame asking different questions** (`GiveFields` / `SaveFields`, Ai-Flow GC/SP) — the heading is the step's own name and the sub says what the choice really does (*Anyone can use and build on this, for free. Minting keeps your name on it — and this cannot be undone.* · *Only you can see this. Minting keeps your name on it — you can share or sell it later.*). Then the same product card, **Blockchain Mint** and **Choose collection** the sale uses — one shared `CollectionField` over the wallet's per-chain rows, so all three forms pick a collection the same way — and, for a give, **License**: the seven licences (Boost 1.0 · BSD 2-Clause · BSD 3-Clause · Creative Commons Legal Code · GPL v2 · LGPL 2.1 · MIT), each with a ⓘ saying what it asks of whoever picks the work up (*Copyleft; derivatives must stay open under GPL*), under the placeholder **Select a license**. Both end on the two confirms every intent shares (**I confirm I am the rightful owner of this idea** · **Share to Innovations**, which reveals the same story panel plus the brand-ink note **Next you will make a short clip — Innovations posts need one.** — here the clip comes *after* the form). The CTA names what it does — **Give to the community** / **Save as Private**, or **Continue to video ›** when Share put a preview next — and stays shut until the form is answered, its tooltip naming the first missing field (chain · collection · licence · the owner confirm). **Gone with the rebuild:** *Recipient community* and *Distribution rule* — the fields left `BriefState` too, so nothing is persisted for a form that no longer asks (an older draft carrying them still opens) —, the *Mint on blockchain?* toggle (the form asks for a chain and a collection, so the mint is not optional), the gas confirm, and the cost card — a give and a save name no price, so its figures would have been the only money on a screen with nothing to check them against; the blue wallet callout stays, because gas is still charged.
- **Prompt Help** (`brief/prompt-help-modal.tsx`) — Step 2's **Help me write it** link has a modal behind it (the handler comes from `brief-app`, so the link shows): *Turn your idea into a video prompt*. The **Write your idea** box opens on what Step 1 already knows (product name + one-liner), **Generate a prompt** asks `/api/refine` in its new **`mode: "video"`** — a system prompt that rewrites the idea as one 10-second scene (subject · setting · camera move · lighting · mood) — and the **Refined prompt** comes back editable, with a copy button that only says *Copied* once the clipboard write has resolved. **Use this prompt** writes it into the Step 2 video prompt; **Regenerate** re-runs, both disabled until there is a result. The model being unreachable is not an error here: route and modal fall back to the same deterministic sentence (`lib/brief/video-prompt.ts` — the shared home, so they can't drift), never a provider error. Escape, the ×, or the overlay closes it and focus goes back to the link.
- **The preview step commits when it is the last one** (`brief/step-2-video.tsx`) — giving or saving with *Share to Innovations* puts the clip after the form, so the footer's forward button *is* the mint, and it names what it commits to: **Give to community and post to Innovations** · **Save as Private** (a sale keeps **Continue to mint setup**, since its form still follows). It drops the forward chevron, because a commit goes nowhere. The press that only *starts the render* still reads **Continue** — that one leaves you standing here. While `commit()` runs the button is a spinner and **Minting…** / **Saving…**, and really disabled, the way the form step's CTA already behaved; it used to stay pressable through the whole write, so the same brief could be committed twice. **The separate “Skip media” link is gone altogether** — it could only be honest where skipping is allowed *and* a step still follows, and `stepsFor` leaves those two no overlap (Sell/Give lock skipping; a Save brief only reaches this step with *Share to Innovations* on, which puts the preview last), so the link never rendered and its handler was dead. The Skip **card** above makes the same choice in one click and the CTA then names what it commits to. The status line beside the button also stops repeating *the render keeps running* when the note above the rule has just said it. Once the clip has rendered the step stops describing a render in flight — *Video ready.* replaces *Render in flight · you can leave any time*, and the *the render keeps running either way* note goes. The global render toast says *Video rendering · <title> · about N min left* and *Video ready · <title>* — no *Project goes live when done* before anything is minted, and no *Tap to review* on a desktop.
- **The clip has two modals, not one** (both, and the regenerate confirm over them, sit behind the flow's one backdrop at the semantic `--z-modal` / `--z-popover` levels — they had their own black 55% wash at z-index 100 and 110, under every toast) (`brief/review-modal.tsx`, `variant`) — **preview**, which the form step's product card opens: **Auto-Generated Preview** with a green **Ready** badge in the header (amber **Rendering** for a clip that hasn't landed — today the card only offers the modal once there is one to watch), the 16:9 clip with play, *Watch the full clip before approving. Once you mint, this is the version that ships with the listing.*, and a footer of **Made from your 3D model** + an outlined **Regenerate** that asks first through the existing `RegenerateConfirm`. **approve** is the global render indicator's path, unchanged — *Review your video*, the ×, **Looks good · continue to mint**, *Not happy with the result?* + *Edit prompt & regenerate*. The preview carries no × (the badge sits where it would), so **Escape** closes it — the confirm on top first, then the clip.
- **Step 4 says what really happened** (`brief/step-4-success.tsx`) — the sublines were written when every brief made a clip, so a give without *Share to Innovations*, which never reaches the preview step, was told *Your video is final*. The copy is composed from the sequence that actually ran: the video is named only where there is one, and **Your post is up on Innovations.** is added when the post was ticked (a save still waiting on its render reads *Stored in your library. We'll post it to Innovations the moment the video finishes.*). Headings — **Listing is minted · Drop is live · Saved** (a sale is *minted*, not live: the marketplace is not open, so nothing claims buyers can see it, and the subline says it goes on sale when the marketplace opens), *Mint complete* while the render finishes — and the line is plain text now instead of `dangerouslySetInnerHTML` over an escaped entity. **The card under the storyboard says the same thing** (`pendingCardLine`): it used to promise *Project goes live as soon as your … video finishes*, which contradicts a save that is already stored, and pointed at *the email you set on Step 3* — a numbered step the named order retired, and the wrong place besides (the reminder is set on the render card). It now names the intent's own outcome (*Your listing goes live* · *The drop opens* · *Your Innovations post goes up* · for a plain save, *It is replaced by your 480p 10s video*) and the notification line is what the app really does.
- **The rail reads even off-sequence** (`brief/brief-rail.tsx`) — the regenerate hand-off forces the preview step whatever the intent runs, and `steps.indexOf(current)` then returned −1, so no row read done *or* active and the whole rail went blank exactly when the user had been dropped into the middle of it; rows are ranked against the canonical **`STEP_ORDER`** (exported from `lib/brief/types.ts`, so the wizard, the draft migration and the rail read one order) whenever the current step isn't in the sequence: the steps already answered tick, and the **nearest row by that order reads as active** (ties to the earlier, the way the wizard's own `stepBefore` places an off-sequence step) and is not also ticked. Ranking only the ticks left an old give/save draft stored at the numeric step 2 — which migrates to `preview`, a step its sequence doesn't run — showing a rail with nothing active at all. The row you are standing on is **`aria-disabled`, not `disabled`**: it carries `aria-current="step"`, which a disabled button neither announces nor lets the keyboard reach.
- **A hand-off refuses only on a brief someone really wrote** (`brief/brief-app.tsx` `draftHasWork`) — Step 1 can attach the build to another project, and that project's own brief wins if it holds work. But the Brief adopts the active project's **product name** on mount and the persist effect flushes it, so merely *opening* a project's brief once wrote a draft that read as work: every later hand-off into it was refused and the answers just typed appeared to vanish. A name is now only work while it differs from the name the project already carries — anything actually answered (description · intent · storyboard · render · mint) still counts. And when the refusal is real, **the notice says where the answers went**: they stay in the brief they were typed in, which it names (*What you just typed is still in Quebec's brief*). **The rail is locked while the commit runs** — `onGo` was only withheld on success, so a rail click during the ~1400 ms write navigated and the commit then yanked the user to Done behind their back — and the commit body is wrapped in `try/finally`, so a throw mid-write can no longer leave the CTA disabled with no way on and no way back.
