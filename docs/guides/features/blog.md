## Blog (`/blog`, `lib/blog`, `components/blog`)
- **One entry is an article; the IDEEZA team reads it before it goes live.** Five statuses a writer learns once, each with one sentence and its own next step (`lib/blog/status.ts`, derived from the record, never stored): **Draft · In review · Needs changes · Live · Taken down**, plus a ★ **Featured** badge and **Changes in review** on a live article whose edits wait. Badges are DS A17 with their word (never colour alone, never the error badge, never violet).
- **Your articles** (`/blog`, `components/blog/list/`): status tabs with counts (All · Drafts · In review · Needs changes · Live; arrow keys), a title search, `?tab=&q=&page=` in the URL, 12 a page, a polite count line. A table from a 600 px box, cards below. A row's title is its one link: the editor for a draft or one that needs changes, the article page otherwise; it shows the cover, category, status, "n things to fix" / "Unsent changes" / "Update needs changes" and the last change in the status's words ("Sent just now", "Live since Oct 14"). The ⋯ holds only what the row can't do, by status: Draft and Needs changes → Delete; In review → Edit (asks to take it out of review first — the team reads exactly what was sent) · Delete; Live → Copy link · Change cover · Edit · Take offline · Delete; Changes in review → Copy link · Discard changes · Delete; Taken down → Delete. Deletes say what they do for that status. First visit teaches the three steps (You write → IDEEZA team reads it → It goes live); empty tabs, no match and a store that can't be read each say so.
- **The editor** (`/blog/new`, `/blog/[slug]/edit`, `components/blog/editor/`, TipTap v3 loaded only here): a title and the article, nothing else — category, topics and the cover wait for sending. Nothing is stored until there is something to keep; then the address becomes the article's own without losing the caret. "+" beside an empty line and "/" add Heading, Subheading, Image, Images side by side (2 or 3, stacking on phones), Video (MP4/WebM ≤ 50 MB), Bulleted and Numbered lists, Code, Quote, Divider, an IDEEZA project card; a new block goes after what is selected, never over it. The selection bubble does Bold, Link (⌘K, http/https/mailto only), Heading, Subheading, Quote; markdown shortcuts work; no italic (Manrope has none). Images ask for a description (or "decoration only") and show "No description" until they have one; pasted text keeps only the article's own marks, pasted remote pictures are dropped with a toast. Autosave ("Saving… / Saved 4:12 PM / Couldn't save · Try again"), a banner when another tab saved, and "Discard changes?" only when a save failed. An article in review is read-only until taken out of review; one that needs changes shows **What to change** above the title. Phones get one top row (Back, save state, ⋯, Send) and a format bar above the keyboard with a labelled Add sheet.
- **Send for review** (`components/blog/send/`): the editor checks the title, the body, uploads and that the latest text is saved, then one column asks for the cover (the article's first image, picked for you; drag, arrow keys, zoom −/+, Center image, another article image or an upload), its description, the Category (required; Build story · How-to · Electronics & PCB · Firmware & code · 3D & mechanical · Robotics · Manufacturing · Selling hardware), up to 5 Topics, About a project (your projects) and, under More options, **Let IDEEZA reuse this article** — unticked until the writer ticks it. The button says what happens: Send for review · Send again · Send changes for review; the list then shows it In review with a toast. Choices are kept when the writer goes back to editing.
- **Demo review** (`lib/blog/demo-review.ts`, labelled wherever it shows): with no backend, an automatic check decides about a minute after sending, on any page (the sidebar's clock) or when a page next reads the article — fewer than 150 words, 400+ words with no heading, or ad-like links/capitals/repeats send it back with how to fix each; otherwise it goes live and its body is copied to the live version. It never features or takes down an article.
- **Review results in the bell**: "“…” is live on the IDEEZA Blog" / "The IDEEZA team asked for changes to “…” · n things to fix" — opening one marks it seen and lands on the article page or the editor.
- **The article page** (`/blog/[slug]`, `components/blog/article/`): one status card holds the status, its sentence and its actions (reasons with the demo label and "Edit article" when changes were asked; Earlier reviews), then the article as readers see it — title (DS H2), byline, read time, the 3:2 cover, prose at 16/24 with underlined links that open a new tab, images, image rows, video, project cards. The rail has **On this page** (scroll-spy on `<main>`), Category and topics, About a project and the reuse switch. Live articles read their live version; a cover from the article's own photos changes at once, a new upload waits for the next review. `/blog/[slug]/preview` shows the draft in the same view under a Preview bar.
- **Store:** `ideeza:blog` (the index, read-modify-write on the freshest copy, never written over when unreadable), `ideeza:blog:doc:<id>` / `ideeza:blog:live:<id>` (bodies with a `rev`), files in IndexedDB `ideeza-blog`. Bodies are BlogDoc v1 JSON, normalised on every read and drawn as React elements; no blog code injects HTML (guard test).
