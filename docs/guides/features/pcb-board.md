## PCB 2D canvas — visualisation (#126 · #127 · #130 · #140 · #141)
- **The board has its own state vocabulary on top of the shared canvas one** — hover · selected · net highlight come from the shared tokens, and the board adds **routing** (`--color-pcb-routing` + glow on the live draft, drawn along the path the track will really take) and **violation** (`--color-pcb-violation`). Captured from the running editor in both themes in the **PCB canvas states sheet** artifact, which also documents the rules (one vocabulary per state, hover suppressed while a tool is armed, selection never recolours the object, dim rather than hide).
- **The board itself is themed** (`--color-pcb-substrate` / `-edge`, `--color-pcb-bed`) — `pcb-canvas.tsx` no longer hardcodes `#0d3b24`, and the light theme gets a paler substrate with darker documentation ink (verified: substrate resolves to `#14532d` dark / green-700 light, board edge `--color-pcb-outline`).
- **Drawing objects have standard colours** (`DRAW_COLOR` + `--color-draw-*`) — line/polyline · rectangle/circle/ellipse · arc/bezier · dimension · text/note/table · keep-out each get one token, applied by both the glyph renderer and the wire overlay, so a board's non-copper marks read as a family (verified: a placed line strokes `var(--color-draw-line)`). A colour set on the object still wins, and a layer colour still wins for copper.
- **2D renders in layer order** (`ordered` in `placed-objects.tsx`) — bottom copper → inner → top → mask/paste/silk → outline/document, so a bottom track can no longer sit on top of a top track, and the 2D stack matches the 3D one. **Focus active layer** (`state.focusActiveLayer`, toggled from the layer strip) drops everything off the active layer to `--pcb-dim-opacity` (30%) instead of hiding it. **One predicate, every renderer** (`isDim` in `placed-objects.tsx`): it used to reach only `PlacedGlyph`, so the toast said “Other layers dimmed” while every **track, wire, cutout, board outline and poured region** stayed at full strength — they all read it now.
- **Long menus stay inside the window** (UIUX-41, `MenuPanel` in `menu-bar.tsx`) — Insert is taller than a short viewport, and the tail simply ran off the bottom with no way to reach it; the panel is capped to what's left under the bar and scrolls internally (verified at 620 px tall: menu ends inside the window, last row scrolls into view). **Its submenus portal to `<body>`** (`MenuRow`): that scroll container clipped every flyout — a child at `left: 100%` is outside the panel's box, so *no* submenu in any menu was reachable. Each one is now `position: fixed`, measured off its row, flipped left near the right edge and lifted near the bottom, opened by hover with a short grace period so the pointer can cross the gap. The menu's click-outside guard skips `[data-menu-flyout]`, since a press in a portalled flyout is still inside the menu. Verified: hover opens it with its real rows fully on screen, moving to a sibling swaps it, and a click inside really arms the tool.
- **A layer strip sits under the canvas** (`LayerStrip` in `bottom-bar.tsx`) — colour chip + name per layer with the active one lit, an eye per layer, and the **Focus** toggle; it is where you *pick* the layer, while the right panel's Layer tab keeps the settings — **and the code now matches that split**, which it didn't: the tab also carried a per-layer eye and set the active layer on a row click, so both surfaces did the same two jobs. The line is now exact — **per-layer** (which layer you draw on · show/hide) is the strip's alone; **what a layer is** (colour · transparency · lock) and **bulk** operations (the All row, the visibility presets) are the tab's alone. A hidden layer still *reads* as hidden in the tab (its name dims to 0.45) — it just isn't toggled there. Verified: 12 eyes on the strip, 1 in the tab (the All row), and clicking a tab row leaves the active layer where the strip put it. The **status bar's own `Layer:` dropdown is gone**: it was a second layer picker two rows below this one. With the right panel open the strip runs out of room, so it **scrolls and says so** (UIUX-55): chips never shrink (a half-word layer name is worse than a scroll), the row **snaps chip-by-chip** so a gesture can't leave one cut in half, and the edge it can still scroll toward **fades out** instead of ending in a hard cut. The palette's variant strip carries the arrow cue and the hit area but **no hover fill of its own** — a second box under the glyph read as a bottom-heavy highlight (UIUX-46). Every control in the strip is a **24 px target** (WCAG 2.5.8) inside a 34 px strip and carries the shared `.ix-tool` / `.ix-pill` states, and the eye is the **same glyph the Layer tab uses** instead of the `◉` / `◌` text circles it used to print (verified: 34 px strip, 0 targets under 24×24, 12 eye glyphs, no text circles).
- **Every board kind resolves to a real Properties panel** (#129) — an audit over `PLACE_TOOLS ∪ DRAFT_TOOLS` found three unmapped kinds (`boardOutlineRect` · `boardOutlineCircle` · `lengthTune`); with those mapped the audit reports **60 kinds, 0 unmapped**.

## PCB editor
- 2D board canvas + layers + grid; **3D view** (three.js). **Flip Board** (mirror the view to inspect the bottom).
- **Parts look like the parts they are** (UIUX-2, `bodyShape` + `PcbBodyMesh`) — every footprint used to extrude the same black box. The land pattern and the designator now pick a **body shape**: a **chip** (dark body with a tinned cap at each end), a **diode** (barrel lying along the part, cathode band, leads), an **IC** (moulded body with its pin-1 dot), a **can** (upright cylinder with a crimped rim) or a **connector** (base plus a raised housing wall) — all built from the land pattern's own dimensions, so nothing needs a 3D asset library. **Silkscreen is printed marking, not just an outline**: the designator is drawn to a canvas texture and laid on the board beside its part, at the silk's own finish colour (so Standard vs UV still changes it). And the **slab has a real edge**: its two faces carry the solder mask while the four sides show the routed substrate, which is what a routed board edge looks like. Verified in a SwiftShader browser: the mask dominates the faces, a distinct substrate tone paints the edge, terminals and several body tones read apart, and `R1 · C1 · L1 · D1 · U1` are printed on the board.
- **Real 3D view of the PCB 2D** (`pcb-scene.ts` `derivePcbScene` + `pcb-meshes.tsx` `PcbSceneMeshes`) — the 3D tab mirrors the 2D layout 1:1: every physical object placed on the canvas becomes real 3D geometry — **board slab** (from `pcbBoard`, real thickness/colour — or from the **drawn Board Outline** when there is one, so a circular or polygon board is extruded as that shape via `THREE.Shape` + `absarc`/ring, and its cutouts are real holes), **copper tracks** (gold ribbons on top/bottom per `layer`), **vias** (copper barrel + plated hole), **footprint pads** (gold, offsets from `PAD_OFFSETS` so they can't drift), **component bodies** (per-glyph size, colour by designator R/C/L/D/IC) and **copper regions/pours**. All canvas-px coords map into one centred, board-size-normalized scene (longest side → 8 units) so camera framing is board-independent. Dedicated to the PCB 3D tab — the coarser `derivePcb3D` (board + boxes) still backs the Product Preview unchanged. Live-driven by the 3D Properties (Board Color/Thickness, Background). *(three.js needs a real/SwiftShader WebGL context — headless verification uses `--enable-unsafe-swiftshader --use-gl=angle --use-angle=swiftshader`.)*
- **3D view-control toolbar** — the 3D mode is a read-only inspection view, so the top toolbar drops the 2D editing set and shows a dedicated view cluster (each drives the three.js camera/render for real, no stubs): **Fit** (frame board) · view presets **Top / Iso / Bottom** · **Perspective↔Orthographic** toggle · **Explode** (lifts the layer stack apart — top copper up, bottom copper down, bodies highest). State in `state.pcb3d` (session-only: `projection/explode/preset/fitNonce/presetNonce`), driven by `pcb3dFit/pcb3dPreset/pcb3dToggleProjection/pcb3dToggleExplode`; a `CameraRig` inside the Canvas applies preset snaps/fit off the nonces and the camera swaps `PerspectiveCamera`↔`OrthographicCamera`. The old stub "Floating Tools" panels over the 3D canvas are removed.
- **The toolbar folds instead of being clipped** (UIUX-45/74, `useFitCount` in `toolbar.tsx`) — the essentials row is `overflow: hidden`, so opening the side panels used to cut its tail off (measured: 7 of 16 controls past the right edge at 1280 px with both panels open). Item widths are measured once, a `ResizeObserver` recomputes what fits, and the remainder moves into the existing **“…” menu** — which the board bar already had and the schematic bar now grows when it needs one. Verified: 0 clipped at 1280 px with the folded controls reachable in the menu, and the whole row back inline at 1920 px.
- **Render style is a setting, not two dead rows** (UIUX-89, `state.renderStyle`) — View carried *2D View · 3D View · Normal View · Outline View* as plain rows with no active state, and Normal/Outline only toasted. **2D/3D left the menu** (the toolbar's own toggle owns that state; two controls for one setting can disagree) and Normal/Outline became **one segmented control** in the menu (`seg` row kind in `menu-bar.tsx`) showing which is active. **Outline view is real, in both views**: the board's glyphs paint in `currentColor`, so one CSS rule drops their fill and strokes the same colour — every pad, via, region and body becomes its own outline while text keeps its fill; **tracks and buses draw their true capsule outline** (two edges + round caps, computed from the run's real width) rather than a thinner solid bar; and in **3D** the same style renders the scene as wireframe. It persists with the document like the grid style. **Flip Board** stayed a plain action — and got the handler it never had.
- **One Help, one home** (UIUX-42) — and **one cart, or none** (UIUX-43): the top bar's shopping-cart button answered to nothing and has no store page to open (the sidebar's own *Explore marketplace* link has no route behind it either), so it is gone until that page exists rather than sitting as decoration. — the global top bar carried a second “?” button beside the cart that answered to nothing; the editor's menu row (⚙ Setting · ? Help) keeps the one that opens a real menu.
- **Left tool palette** (shared `ToolPalette`) — the board's modal tools, reshaped to the client's list. **Neither palette carries a selection row** (UIUX-7/11): selecting is what the pointer does by default (drag rubber-bands, Esc returns to it) and panning is H / hold-Space, so the row was a tool for the thing that needs no tool. **Route** (Track · Diff-pair · Length-Tuning) · **Pads & holes** (Pad · Shaped Pad · **Mounting**, which left the Design menu so it has one home · UIUX-12) · **Board Outline** (**Rectangle · Circle · Polygon** — see below) · **Region** (Copper · Slot · Prohibited · Constraint) · **Shapes** (Line · Polyline · **Rectangle · Circle · Ellipse · Arc**) · **Dimension** · **Text**. *Removed with their tools: **FPC Stiffener** and **Via Fence** (both placed a glyph with nothing behind it and had no other home), plus the **Eraser** row — Del · Edit ▸ Delete · right-click already delete.*
- **The board outline is a real shape** (`boardOutlineRect` / `boardOutlineCircle` in `DRAFT_TOOLS`, `boardOutlinePoly` + `state.draftPoly`) — Rectangle and Circle are **dragged** (corner-to-corner, centre-to-radius), Polygon is **clicked** vertex by vertex and closes on **Enter**, a **double-click**, or clicking the first vertex again; Esc cancels. Each commits a `boardOutline` object carrying `props.shape` plus its geometry (rect/circle in `width`/`height`, polygon as a `points` ring) and renders as that shape in the Board-Outline colour. Verified live: `rect 280×200`, `circle 216×216`, `polygon 160×150` from real drags/clicks. It left the top toolbar (`HOMED_KEYS`) because only the palette flyout can carry three variants.
- **Layer/entity colors are token-driven** (`tokens.css --color-pcb-*`, sourced from the base palette) — copper identity is locked (**Top = red, Bottom = blue**), other layers get distinct non-competing hues; canvas states use `--color-canvas-highlight` / `--color-canvas-select`. Per-layer color/transparency/visibility is editable in the Layer Manager (the swatch resolves a token `var()` → hex for the native picker).
- Pads, vias, tracks, copper-pour polygons, fill regions, slots, board outline, etc.
- **Selection Filter** (`boardSettings` + `isSelectable`) — right-click "Only Track/Pad·Via/Copper" and schematic "Only Pin/Symbol/Wire&Bus/Pin-Pair/Net", plus the two **Filter-tab key filters**: the board list (`FILTER_KEY_FOR_KIND`) and the schematic list (`SCHEM_FILTER_ROWS` / `SCHEM_FILTER_KEY_FOR_KIND`) — see the right-panel entry.

## Board areas are drawn, not stamped (UIUX-86 · 87 · 92 · 97)
Every area — **Copper Area · Fill Area · Slot · Prohibited · Constraint · Cutout** — takes the board outline's three shapes: **Rectangle** and **Circle** are dragged, **Polygon** is clicked vertex by vertex and closes on Enter, a double-click or the first vertex. One vocabulary carries it (`types.ts`): the tool id names the kind and the shape (`area:slot:polygon`), `parseAreaTool` / `isDraftTool` / `isPolyTool` route the drafting, and the committed object stores `props.shape` plus its real geometry (rect: `x/y` top-left + `width/height`; circle: centre + diameter; polygon: a `points` ring). `shapeToPolygon` reads that geometry, so a drawn area **pours, clears, DRCs and exports at its real size** — before this every region was a fixed 28×20 stamp. The **palette's Region flyout** lists the kinds with their shapes one level down (one shared picker, not six copies) and the **menus** carry the same submenu on Edit ▸ Cutout, Insert ▸ Slot/Prohibited/Constraint and Design ▸ Copper Area/Fill Area. **Polygon Pour** is its own row at the top of the flyout (and in Design): draw a copper ring and it fills the moment it closes (`armPolygonPour` → `draftPoly.pourOnClose` → `pourRegions`). **Copper Area and Fill Area live in Insert** (UIUX-96) beside the other regions — they are things you *place*, so the Design menu keeps only the pour work they feed (Polygon Pour · Pour/Rebuild copper · Remove all pours). The two also stopped sharing one pentagon: **`tCopperArea`** is solid metal, **`tFillArea`** the same outline hatched, the way a poured zone is drawn on a fabrication print. Fixed on the way: placed objects swallowed clicks while an area tool was armed, so a vertex dropped over an existing region was eaten by it.

## Teardrops (`teardrops.ts`)
**Design ▸ Teardrop** (UIUX-88) — real copper fillets where a track meets a pad or via, not a label: for each same-net joint `planTeardrops` builds the drop outline (the pad's far arc swept, then out to the track's half-width a distance down the run) and stores it as a `points` polygon on the track's layer, so the canvas, the 3D scene, the DRC and the exporters read it like any copper. Add to all joints · Add to selected tracks (greyed with a reason when nothing is selected) · Remove all teardrops. Each drop carries `props.teardropFor`, so a second run skips the joints that already have one and says so, and removal finds exactly what it made. **Design ▸ Fill All Planes** re-pours every copper region on the board in one action (the same engine as Pour/Rebuild, so the result is identical to pouring them one by one).

## Copper pour (`pour.ts`)
`pourCopper(state, ids?)` turns a placed copper region into **real copper**: the region outline minus every other-net track/pad/via/line grown by the Cu-Zone clearance, cut with the app's own boolean engine, stored as a `points` polygon (so the canvas, the 3D regions and the DXF/SVG exports all read it). The original outline is kept in `props.pourOutline`, so re-pouring never shrinks the region, and same-net copper is deliberately not cut away (it joins the pour). Design ▸ **Copper Region · Fill Region · Pour / Rebuild copper · Remove all pours** — verified: place a region → Pour → `Poured 1 region` with a real polygon on the canvas; Remove all pours → `Removed the pour from 1 region` and the polygon is gone. *(Thermal spokes on pads and island removal aren't modelled yet — a pad is cut with plain clearance.)*

## Board-document, part & module authoring (#79) + Move (#86) + schematic sync (#93)
- **Project ▸ New** — on the **board it is PCB alone** (UIUX-75: the PCB is downstream of the sheet, so a part authored there would have no symbol to come from); the **schematic** keeps the authoring rows. PCB creates the board document for a project that has none (and says so honestly when one exists), **Part…** authors a catalogue row into the personal library (`ideeza:pcb:personalParts` → `allParts()`, so it appears in the picker's **Personal** rail with every filter and the Place button working — verified end-to-end), **Agile Module…** captures the current selection as a named reusable block (`ideeza:pcb:personalModules`).
- **Move asks what to move when nothing is selected** (UIUX-94, `state.movePick` + `pickMoveTarget`) — it used to close the menu and do nothing at all. Now the hint chip says *Nothing selected — click the object to move · Esc cancels* and **stays up** until answered; the next canvas click is consumed before any pan/marquee intent and grabs that object (its whole group, if it is in one). Selection and grab happen in **one** state update: selecting first and then calling `startMoveSelected` read `stateRef` before React had applied the selection, so the move saw an empty selection and re-asked.
- **Edit ▸ Move** now grabs the selection for real (`startMoveSelected`) — the old rows armed `setTool("move")`, which has no handler, so nothing moved — and **Move by step…** nudges by the grid step or an exact dx/dy (`moveSelectedBy`, verified: 14 objects moved exactly 5 px right, `Moved 14 objects by 5, 0`). *Move by step is gone from both Edit menus (UIUX-34 then UIUX-21) — grid + snap cover placement on the sheet and the board alike — and its dialog, modal id and `moveSelectedBy` action went with it rather than sitting unreachable. Grab-move (M) is the Move both menus carry.*
- **Design ▸ Import Changes From Schematic** (`importChangesFromSchematic`) replaces the old “Update PCB to Schematic”, which only switched tabs: it re-runs the converter, **keeps the placement/rotation/side of parts already on the board** (matched by `sourceId`), adds the new ones, drops the ones whose symbol is gone, rebuilds the ratsnest, and leaves hand-drawn tracks/vias/regions alone. Verified idempotent — running it twice changes nothing.

## Native Schematic → PCB (`schematic-to-pcb.ts`)
- Pin-level netlist from wire connectivity → real footprints → pad-to-pad **ratsnest** → BFS auto-placement (decoupling caps near their IC) → L-shaped **auto-route**. Auto-runs on the Schematic→PCB switch. Footprints store `sourceId` for **Cross Probe**.
- **Auto Routing is one engine with real options** (`routeRatsnest(objects, width, opts)` + `actions.autoRoute(opts)`) — the toolbar's **Auto Routing** dialog used to toast "Auto routing started…" while only the Route menu actually routed. It now runs the same engine, and every control changes the result: **Scope** — *Unrouted nets only* · *Selected nets* (airwires whose net is in the selection) · *All nets (re-route)*, which hands previously generated copper back as airwires first (`unrouteGenerated` regroups the `pcb-trk-<airwire>-<n>` segments the router stamps, so each pair of endpoints is recovered exactly) — each option showing its live count, and the run disabled when a scope has nothing to do; **Use each net's class track width** routes from `pcbNetClasses`; **Mitre corners to 45°** emits three segments (leg · diagonal · leg) instead of a right angle. The fake *Strategy* radio group (Fast/Balanced/High quality) is gone — the router has one strategy — and the dialog states plainly that it does not push existing copper aside yet. Verified live: `Auto-routed 1 connection → copper tracks (45° corners)`.

## Interactive routing — corner style + obstacle policy (`route-path.ts`)
`planTrackPath(state, from, to)` decides the polyline a drafted track really takes, and the **draft preview and the commit call the same planner**, so the dashed path is what lands. **Routing Corner is two choices, not one list** (UIUX-91, `CORNER_STYLES`) — the **shape** of the bend (a straight miter or a rounded arc) and the **angle** its legs are held to (45° · 90° · free) — so the menu carries the six combinations in two groups: **Line 45° · Line 90° · Line Free Angle │ Arc 45° · Arc 90° · Arc Free Angle** (the old flat *Any angle / 45° / 90°* conflated the two and had no arc at all; stored ids migrate on load). The arcs are real tangent geometry (`roundCorners`: trim `r/tan(θ/2)` down each leg, centre on the bisector, sampled in 10 steps) — **Arc 45°/90°** round the bend at a modest radius and keep their straight legs, while **Arc Free Angle** opens the radius until the legs are gone and the run is one curve; a leg shared with the next corner still gives up only half of itself, so an oversized radius can't fold the run. Verified live: Line 90° commits a sharp L (2 segments, one turn), Line 45° a diagonal + leg, Line Free Angle one straight run, and each arc commits 11–12 segments turning gradually — Arc 90° keeping a 187 px straight leg where Arc Free Angle's longest is 40 px. **Routing Mode** is the obstacle policy: **Ignore** draws through, **Walk around** tries the mirrored corner then a detour clear of the blocker's extent (verified: a run that would have crossed a vertical track came out as a real 3-segment detour below it), **Push** shoves the blocking track sideways by one clearance step when that leaves both paths clear. Clearance comes from the tuned rules (`pcbDrcConfig` Track↔Track, else 0.102 mm) and the geometry is exact segment-to-segment distance. Both menus were **cosmetic before** — `state.routingMode`/`routingCorner` were written and never read, and Routing Mode listed 45°/90°/Curved, which are corner shapes; the right panel's duplicate (dead `boardSettings.routingMode`) is gone, so the Route menu is the one home. *Honest limit: a same-layer **crossing** can't be resolved by shoving copper sideways (that needs a layer change), so Push falls back to the detour and says so in the status toast rather than pretending.*

## Native PCB DRC engine (`drc.ts`) — the PCB counterpart of the schematic ERC
- **Its dialog is IDEEZA's own shell** (UIUX-90, `PcbDrcModal`, titled **Board constraints**) — the EasyEDA transcription is gone end to end, not just recoloured. **Two destinations replace the four tabs** (Rule Management · Net Rule · Net-Net Rule · Region Rule): **Limits** — the constraints themselves — and **Where they apply**, one surface carrying a *Nets · Net pairs · Regions* scope switch, because "which net, which pair, which region" is one question and three of the four tabs were assignment tables. The **unit** and the **all-layers / per-layer** scope left the rule form for the dialog's own bar (they govern every rule, and the `Unit: mm` + `All/Layered` radio row was EasyEDA's). The **rail lists the limits themselves**, split by the only thing that changes whether one matters — **Checked by the engine** vs **Not checked yet** (`DRC_ENFORCED_LEAVES` = Safe Spacing · Track · Via Size · Net Length Range · Differential Pair, the drc.ts phases) — with the rule type as each row's sub-line, so a category→type→rule tree collapses to one honest list; **+ Add a limit…** is one control naming every kind (grouped by category, marking the unchecked ones) instead of a `+` hidden on each of twenty-four tree rows. The rule's **name is the editable heading of its own editor**, `Board default` a toggle chip beside it and `Delete` a quiet action — replacing the `Name: [ ] Default [Delete]` chrome row. An **Only what the engine checks** toggle and a **search** sit at the rail's head. **The footer carries the decision alone** (Cancel · Save · **Save & check now**, which saves, closes and really runs the DRC — verified: the bottom DRC panel came back with `Fatal 0 · Error 2`); the set-level actions — fab preset · **Import a constraint set… · Export this constraint set · Restore “<limit>”** — moved to the foot of the rail under *Whole constraint set*.
- **Minimum spacing is a base plus its exceptions, not a 91-cell grid** (UIUX-90, `SpacingEditor`) — the clearance matrix was a cell-for-cell transcription *and* a poor way to read the rule: 90 of 91 pairs carry one of five numbers, so the grid spent its whole area repeating one value and hid the handful that matter. It now leads with the **base spacing** (the value most pairs already carry, stated as `Used by 52 of 90 pairs — changing it moves all of them`, and editing it rewrites exactly those), then **Types that keep their own spacing** — one collapsible row per object type that differs, showing its value (or `mixed`) and its pair count, expanding to each pair with its own field and a **use base** reset. The **full pair grid is one disclosure away** (`Show every pair (90)`) for anyone who wants to sweep it, now **tinted by magnitude** (`color-mix` over the brand token) so outliers are visible instead of uniform. The stored `ClearanceRow[]` model and the manufacturing defaults (0.102 / 0.152 / 0.254 / 0.3 / 0.176 mm) are untouched — every value stays editable and `rulesToDrcConfig` reads the same shape.
- **Phase 1 — Safe-Spacing clearance (real geometry):** `runDrc(objects, cfg)` checks every pair of copper objects (track/pad/via/region/fill/slot/line) that can physically conflict — **different net** + **layer-aware** (vias/TH pads are through-layer) — and reports a violation when the real **edge-to-edge clearance** is closer than the type-pair rule. Geometry is exact: segment/capsule distance (tracks + round pads/vias as inflated centre-lines), polygon edge distance + point-in-polygon containment (rect pads, copper regions). The clearance thresholds come from the Design-Rule dialog's **Safe-Spacing matrix** (`defaultClearanceRows()`, mm) via the documented `PX_PER_MM` scale (px geometry ↔ mm rules; linear dims are mil). Findings render live in the bottom **DRC tab** (`state.pcbDrcResults`, severity dots + Fatal/Error/Warn/Info filter chips) — the old static demo rows are gone. Run via the board toolbar's **Run DRC** button, **Design ▸ Run design check (DRC)** or the Tools ▸ Check DRC menu (`runDrcCheck`); the DRC tab is where the findings land and carries no run button of its own, so its empty state names those homes instead. The **PCB Design Rules dialog now drives the engine for real**: its Apply/Confirm maps the rule form → `PcbDrcConfig` (`drc-rules-map.ts` `rulesToDrcConfig` — clearance matrix, track width, via size, net-length, diff-pair skew) into `state.pcbDrcConfig` (persisted), which `runDrcCheck` reads instead of the defaults. *(Fixed a bug where disabling the clearance phase short-circuited physics/connectivity/diff-pair/netlist too — each phase's enable flag is now independent.)*
- **Phase 2 — Physics rules (`runPhysics`):** per-object **track width** (min/max), **via size** (outer + inner/hole diameter min/max), and per-net **net-length range** (min/max) — each flagged at Warning against the `defaultPcbPhysicsRules()` values (mm, transcribed in `design-rules-data.ts` so the dialog + engine can't drift). Reads track `width`/via `drill` (mil→mm) and sums track lengths per net (px→mm).
- **Phase 3 — Connectivity & free copper (`runConnectivity`):** copper that should carry a net (track/pad/via/region/fill) but is **unnetted** → "Free copper"; and same-net copper that doesn't all join geometrically (union-find over touching geometry, `TOUCH_TOL`) → "Disconnected net — N isolated sections". Both at Warning.
- **Phase 4 — Differential pairs + netlist mismatch (`runDiffPairs`/`runNetlist`):** per pair in `state.pcbDiffPairs` — **missing member** (one rail routed, the other not), **width** (track width vs the pair's target), and **length skew** (|len(netA)−len(netB)| vs `diffPairSkewMax`, default 0.5mm) — all at Warning; verified live against the default USB_D pair. **Netlist-mismatch** (`runNetlist`, Fatal for a schematic net absent on PCB, Warning for an extra PCB net) is implemented + unit-tested but **gated off live** in `runDrcCheck` — the Schematic→PCB convert renames nets to `N1…`, so a name comparison would flood every net as missing until the convert preserves net names.
- **Phase 5 — the manager lists are rules (#99)** (`runNetClasses` · `runEqualLength` · `runPadPairs`): a **net class** states the track width and via size its nets must have, an **equal-length group** the window every net must land in (`target ± tolerance`, mil), a **pad-pair group** its target spacing (±10%). All three feed the same DRC results panel, and the dialogs' footers are honest — assignment is live, so the fake “Apply” is gone and **Check now** runs the check that reads them (verified: `Check now` produced real `Equal length group` and `Pad pair group` findings). Before this, `pcbNetClasses` / `pcbEqualLength` / `pcbPadPairs` were stored by their dialogs and read by **nothing**.
- **Pad-pair groups say what they really do** — adding or removing a pair writes the group immediately, so the dialog's old `Apply` (a toast) and `Cancel` (which reverted nothing) were theatre. The footer now reads *N of M grouped · saved as you go* · **Check now** (runs `runDrcCheck` and closes to the results) · **Done**. Pairs are also stored by pad **id**, so reordering the board can't repoint a pair.
- **The three group managers are one list, not two columns** (UIUX-49/50/51, `GroupWorkbench` in `pcb-manager-modals.tsx`) — **Net classes · Matched length groups · Pin pair groups** (renamed from *Net Class Manager* / *Equal Length Group Manager* / *Pad Pair Group Manager*, in the dialog **and** the Design menu, to the terms Altium and KiCad already use). They shared a dual-list transfer shell: a group list with `+`/`−`, then *Not Selected* and *Selected* columns with their own filter boxes and arrows between them — so you held "where is this net?" in your head while shuttling names across two columns, and 200 nets meant hunting the same list twice. The workbench inverts it: **one searchable list of every member, each row carrying the group it belongs to** as its own control. No second column, no arrows, no per-column filters. The rail holds the groups as **cards stating what the group really sets** (`8 mil track · 24 mil via` · `1500 ± 50 mil` · `100 mil target`) with live counts, and doubles as the filter over that one list (All · each group · Unassigned); `New group` is a full-width row, delete is on the card. Membership is now **single** — picking another group moves the net rather than leaving the same name silently in two lists, which the transfer UI allowed. **Pin pair groups** keep the shape but a pair doesn't exist until you make one, so a **composer row** (Pad 1 ↔ Pad 2 → group → *Add pair*) sits above the list and each pair's row carries the same group control, with `— remove —` deleting it; the two-column pad picker with its `>` button and *select pad(s)* placeholder is gone. Footer unchanged in meaning: *N of M grouped · saved as you go* · **Check now** · **Done**.
- *Still not enforced: Board-Outline keep-inside clearance, the Hole matrix row, footprint-baked-pad expansion (converted boards expose pads inside the footprint glyph), text/image copper, diff-pair spacing, net-length tolerance/equal-length groups, and the live netlist-mismatch (pending convert net-name preservation).*
