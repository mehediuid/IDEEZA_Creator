# IDEEZA Creator — Project Guide

`ideeza-creator-panel` — a browser-based **AI-driven hardware-creation
platform**. A maker describes an electronics idea; AI drafts the **schematic,
parts list and build steps**, which the maker refines in a suite of editor
modules (PCB, Code, 3D, Wiring, Preview, Brief), then **mints the design
on-chain (Utility NFT)** and shares/sells it via the community feed and
marketplace. The deepest module is an **EasyEDA-inspired schematic + PCB
editor** with a native (KiCad-less) Schematic→PCB pipeline. This is a **real
product, not a prototype** — every control must do real, verified work.

> **Next.js is modified here.** See `@AGENTS.md`: this is Next 16.x with breaking
> changes. Read `node_modules/next/dist/docs/` before writing any Next-specific
> code.

### State / store (`store.tsx`)

- One `PcbState` object; actions built with `useMemo`.
- **`merge(patch)`** — plain state update (view/UI, no undo).
  **`mergeWithHistory(patch)`** — model changes; snapshots `SNAP_KEYS` for undo/redo (diffed, so no-ops don't pollute history).
- **`stateRef.current`** — read latest state inside async/event actions.
- **`setToolAs(tool, text)`** — arms a place tool whose object carries a given name (`state.placeText`, consumed + cleared by `placeObject`). Lets several menu rows share one symbol kind honestly: Insert ▸ Power & Ground places `vcc5v` as **VCC / +5V / -5V**, and the supply glyph draws `obj.text`.
- Actions may call `actions.<other>()` (safe — invoked on events, not during render).
- **Persistence:** the *document* (`objects, pcbBoard, twoD, threeD, gridSize, gridType, unit, snapEnabled, designRules, pcbDrcConfig, pcbLayers, pcbNets, pcbDefaults, boardSettings`) auto-saves (debounced) to `localStorage` under `ideeza:pcb:doc:<projectId>`, scoped by `ideeza:manual:active`. So layer colours/visibility/lock, net colours, place defaults, grid style and DRC rule-tuning now survive reload. UI flags (zoom, panels, menus, sheets) are session-only. `saveDoc()` force-writes; `sanitizePcbDoc()` shape-checks every key on load.

### `CanvasObject` — the universal placed-object model

`kind, x, y, endX/endY` (wires), `text, rotation, color, layer, net, footprint,
comment, side, props` (typed-field bag), `scope` (`"schematic"|"pcb"`),
`sheetId` (multi-sheet), `sourceId` (cross-probe link), `points` (real polygon
rings for Combine results). Add a field here + handle it in `placed-objects.tsx`
+ (if persisted) the doc sanitizer.

### PCB module — schematic editor
- **One canvas state vocabulary, from tokens** (`tokens.css` "Canvas interaction states" → `placed-objects.tsx`): **hover emphasises the object, not a box around it** (UIUX-25) — every glyph paints in `currentColor`, so hovering takes the `--color-canvas-hover` accent into the symbol itself and thickens its strokes to 2.6 (`.ix-hot`), which reads as the part's own linework, pin numbers and label going bolder; a note's letterforms bolden instead, and an image — which has no strokes — brightens its own frame. It used to draw a plain rounded rectangle around whatever was under the cursor, which is what the ticket objected to. Suppressed while a place/draft tool is armed, because the click then belongs to the tool. **selected** = 1px dashed `--color-canvas-select` + `--color-canvas-select-fill` — a *marker*, so it can never be confused with hover's emphasis; verified across **all 21 schematic entities** (UIUX-26: wire · bus · line · arc · ellipse · bezier · rectangle · polygon · junction · no-connect · power · ground · net label · net flag · port · text · table · image · component · pin · agile module) that each one changes on hover, never boxes, carries a selected state, and that the two differ. Fixed on the way: the **text** object never received the hover handlers at all, and the **image** drew the same dashed frame for hover and selection.
- **Drawing primitives have a standard colour on the sheet too** (UIUX-17, `SCHEM_DRAW_COLOR` + `--color-schem-draw-*`) — the board's `--color-draw-*` are picked to sit on dark green substrate, and the sheet was borrowing them, so a `gray-300` line all but vanished on white paper. The sheet carries its own set with the same meanings — a plain rule · a closed shape · a curve · a note — so the six primitives the ticket names (Line · Circle/Ellipse · Arc · Rectangle · Polygon · Bezier) take four colours rather than six unrelated ones, defined for **both themes** (verified: `#475569` on the white sheet, `#cbd5e1` on the dark one). ### Schematic connectivity, ERC, netlist & annotation (`nets.ts`)
- **Live netlist** — symbol kinds carry pin anchors (`SCHEM_PINS`); `computeNets()` union-finds pins + wire endpoints into nets, named from net-label / power / port symbols (same name merges) else auto `N1…`. Pure/derived — always reflects the drawing.
- **Auto-junction** — a wire ending on another wire's **interior (a T)** is electrically joined (on-segment union) and a **junction dot** is auto-dropped there on wire-finish.
- **Buses are bundles, not conductors** — a bus carries a `PREFIX[lo:hi]` name and **expands to member nets**: `computeNets` excludes buses from the electrical graph, so branch wires connect by member label (`BUS_D3` here = `BUS_D3` there, via same-name merge) and each member is its own net in the netlist. Bus membership (for ERC) is geometric (a pin/branch endpoint on the bus line).
- **Nets tab** (navigator) lists the live nets with object counts; clicking highlights the net (members via connectivity → `highlightedMembers`, since schematic objects have no stored `net`).
- **ERC** (`runErc` + `ERC_RULES` catalog) — a real rule engine over the live connectivity, emitting findings on the EasyEDA-Pro **5-level severity scale** (Note · Warning · Error · **Fatal**). Enforced rules: floating pins, free/dangling wire, single-connection net, label-not-connected, duplicate & unannotated & mis-formatted designators, empty Value, netflag/netport-needs-name, illegal net name (charset/length), illegal bus name, multiple-net-names-on-one-net, global-net short, port/flag/off-page name-vs-wire mismatch, unpaired differential pair, overlapping-unconnected pins (bare pin tips with no wire/junction join), **bus rules** (illegal bus name, bus-branch member naming `PREFIX[lo:hi]`, and netport/netflag/off-page ↔ bus name-match — a bus bundle legitimately carries many member names, so multiple-net-names is suppressed on it), and the **pin-conflict matrix** (Connection tab). Severities live in one catalog (`ERC_RULES`). The pin-conflict rule reads each pin's electrical type (`SCHEM_PIN_TYPES` / `POWER_PIN_TYPE` / `props.pinType`) and looks up the pair in `defaultPinMatrix()` — so two op-amp outputs = Error, Power↔Ground/OUT↔Power = Fatal, while normal passive nets stay clean (matrix default is Ignore; a No-Connect flag suppresses the net). Results show in the bottom **DRC/ERC tab** (Fatal/Errors/Warnings/Notes counts) via "Electrical Rule Check" / Design ▸ Run design check, **and on the canvas** (UIUX-81, `drc-markers.tsx`): each finding names the objects it is about (`ErcIssue.ids`, filled by `emit`), so the offending wire · pin · part · flag is **ringed where it sits** — a dashed circle sized to that element's real bounds and coloured by severity (Fatal · Error · Warning · Note), with the severity dot and its tooltip on the ring. A finding that names nothing keeps the small positional marker, and the bottom tab's **Show on canvas** turns the layer off. Verified against a sheet built to trip one rule per severity: overlapping pins (Fatal), an unnamed Netflag (Error), GND shorted to VCC (Warning) and an unannotated `R?` (Note) — 8 dashed rings, four distinct severity colours, and the shorted wire's ring 232 px wide against a symbol's 32. **Config-driven** — `runErc(objects, cfg)` reads the **Design Rules dialog** config (`state.designRules`, persisted per-project in the doc): a disabled rule is skipped, a re-severitied rule reports at the tuned level, and the pin-conflict matrix + its master toggle come from the config. The dialog (Save → `setDesignRules`) is the real tuning surface, not a stub. **Its shell is IDEEZA's own** (UIUX-39, titled **Electrical rules** — the term the Design menu and the toolbar's ERC control already use; “Design Rules” pointed at the board's dialog): a category rail (Nets & connectivity · Components · **Agile Modules** · Pin conflicts) with per-category *on / total · checked* counts, a whole-config summary (`23 of 35 rules on` + severity chips), a rule filter, an **Only rules the engine checks** toggle and Enable/Disable-shown. **A rule row is one decision, not two controls** — it used to carry EasyEDA's anatomy (a checkbox, a `01`/`02` number, the rule text, a severity badge on the right), where "on" and "how loudly" were separate switches that could contradict each other. The number and the checkbox are gone; the row is the rule text over a state line in words (*Reported as a warning* · *Not reported* · *Not checked yet*) with one **five-stop report level** on the right — **Off · Note · Warn · Error · Fatal** — so the current level and every alternative are visible at once instead of hidden behind a dropdown. `Off` writes `enabled:false` and a level writes `enabled:true` + that severity, so the engine's model is untouched (a stored `Ignore` severity reads as Off rather than leaving the control blank). Rules the engine doesn't implement yet carry a **“not checked yet”** badge (from `ERC_ENFORCED_ROWS`/`ERC_RULE_AT`, exported from `nets.ts` as the inverse of `ERC_TO_DIALOG`) so a toggle never pretends to matter. **The config contract is load-bearing** — `runErc` looks rules up by category + row index, so the dialog never reorders or filters the stored arrays; the search box filters only what is displayed and every row keeps its true index. **Every toggle is keyboard-operable** — the rule rows, the *Only rules the engine checks* filter and the pin-conflict master were `<span onClick>` around a painted box, so Tab never reached the controls that decide what the checker reports; they are `<button role="checkbox" aria-checked>` now (`CheckRow`), and the design-system `Checkbox` gained a `decorative` flag so the painted box inside a labelled control no longer announces a second, nested checkbox role (verified: 0 nested roles). **The footer carries the decision alone** — Cancel (discards the buffer) · **Save & check now** (saves, then really runs `runErcCheck` and opens the results tab — the old “Verify Now” only switched tabs) · Save. ### Interactive routing — corner style + obstacle policy (`route-path.ts`)
`planTrackPath(state, from, to)` decides the polyline a drafted track really takes, and the **draft preview and the commit call the same planner**, so the dashed path is what lands. **Routing Corner is two choices, not one list** (UIUX-91, `CORNER_STYLES`) — the **shape** of the bend (a straight miter or a rounded arc) and the **angle** its legs are held to (45° · 90° · free) — so the menu carries the six combinations in two groups: **Line 45° · Line 90° · Line Free Angle │ Arc 45° · Arc 90° · Arc Free Angle** (the old flat *Any angle / 45° / 90°* conflated the two and had no arc at all; stored ids migrate on load). The arcs are real tangent geometry (`roundCorners`: trim `r/tan(θ/2)` down each leg, centre on the bisector, sampled in 10 steps) — **Arc 45°/90°** round the bend at a modest radius and keep their straight legs, while **Arc Free Angle** opens the radius until the legs are gone and the run is one curve; a leg shared with the next corner still gives up only half of itself, so an oversized radius can't fold the run. Verified live: Line 90° commits a sharp L (2 segments, one turn), Line 45° a diagonal + leg, Line Free Angle one straight run, and each arc commits 11–12 segments turning gradually — Arc 90° keeping a 187 px straight leg where Arc Free Angle's longest is 40 px. **Routing Mode** is the obstacle policy: **Ignore** draws through, **Walk around** tries the mirrored corner then a detour clear of the blocker's extent (verified: a run that would have crossed a vertical track came out as a real 3-segment detour below it), **Push** shoves the blocking track sideways by one clearance step when that leaves both paths clear. Clearance comes from the tuned rules (`pcbDrcConfig` Track↔Track, else 0.102 mm) and the geometry is exact segment-to-segment distance. ## 6. Coding conventions

- **Workflow — use the superpowers skills for code work.** Start any coding task by invoking **`/using-superpowers`**; follow its process flow — **brainstorming** before building a feature, **writing-plans** for multi-step work, **test-driven-development** while implementing, **systematic-debugging** for any bug, and **verification-before-completion** before claiming done. Don't jump straight to editing.
- **Real logic, never stubs.** No button that only `flashToast`s or sets a dead flag. Implement the actual behaviour (correct math — group rotate/flip pivots on the selection centroid; z-order reorders the objects array), then **verify in a real browser**. Be upfront about anything still incomplete.
- **`tsc --noEmit` must pass.** `data.tsx` is `@ts-nocheck` (pure data builders) — everything else is type-checked.
- **Store discipline:** pick `merge` vs `mergeWithHistory` deliberately (model change → history). Read via `stateRef.current` in event/async actions. New persisted state → add to the doc type + sanitizer + save effect.
- **One model:** route new placed things through `CanvasObject` + `placed-objects.tsx` rather than bespoke rendering.
- **Match the surrounding code** — comment density, naming, idiom. Reference files as `path:line`.
- Prefer editing the existing builders (`data.tsx`, `inspector-schema.ts`) over parallel systems.

## 7. UI/UX guidelines

- **Workflow — use `/ui-ux-pro-max` and `/impeccable` for UI/UX work.** Plan and build any interface, visual, layout or design-system change through these skills (they enforce the register, tokens and craft rules below). Reach for them on new surfaces, redesigns, polish passes, and design critiques.
- **Tokens only** — never hardcode color/spacing/radius/shadow. Use `--color-*`, `--spacing-*`, `--radius-*`, `--font-size-*`, `--elevation-*`, `--border-width-*`. Both **light + dark** themes (`data-theme` + `prefers-color-scheme`).
- **Brand = violet** (`--color-violet-600`, #7c2db9). Accent is for **selection / active / primary only** — not decoration. Restrained palette (product register).
- **The design-system `Checkbox` / `Radio` are real controls** (`components/ideeza/checkbox.tsx`) — they announce `role="checkbox"` / `role="radio"`, so they now also take focus (`tabIndex`) and activate on **Space/Enter** whenever they carry an `onChange`; they were mouse-only, which made every labelled row built on them (Sheet Border, Sheet Info fields, Zone reference, dialog toggles) unreachable from the keyboard. A `decorative` flag drops the role for the cases where the box is only the picture inside a labelled `<button role="checkbox">`, so no control announces itself twice.
- **Shared classes** (`pcb-editor.css`): `.ix-tool` (icon button), `.ix-row` / `.ix-mi` (list/menu row), `.ix-menu` / `.ix-submenu`, `.ix-tab`, `.ix-pill`, `.ix-btn`, `.ix-seg`. Reuse them; don't reinvent hover/active states.
- **Icons:** `<DsIcon name={...} size strokeWidth />` — resolves a Hugeicon first, falls back to the SVG-string dictionary.
- **Menus & dropdowns must never clip.** The editor is full of scroll/overflow containers → any flyout **portals to `<body>` with `position: fixed`** and **clamps into the viewport** (flip left near the right edge, shift up near the bottom). Anchor context menus at the cursor.
- **Earned familiarity** — behave like Figma / EasyEDA / KiCad / Linear; the tool disappears into the task. No invented affordances for standard actions.
- **Contextual disable, not stubs** — grey a control when its precondition isn't met (Copy needs a selection, Cross Probe needs a PCB link); light it up when it is. **Empty states teach** ("No nets yet — convert to PCB to generate").
- Motion 150–250 ms, ease-out; state feedback only, no decorative choreography.
- The Position/arrange panel is the reference for dense control layout: equal-size boxes on an aligned grid, segmented icon groups with hairline dividers.

## 8. Scope / direction


Building a **real, shippable product** in phases (schematic → PCB → routing/DRC →
manufacturing/export). The Schematic→PCB engine is **native in-app** (KiCad
export exists via `kicad-export.ts`, but conversion/placement/routing are our
own). Communicate concisely; keep changes tightly scoped to what's asked.
