# IDEEZA Creator — Project Guide

`ideeza-creator-panel` — a browser-based **AI-driven hardware-creation
platform**. A maker describes an electronics idea; AI drafts the **schematic,
parts list and build steps**, which the maker refines in a suite of editor
modules (PCB, Code, 3D, Wiring, Preview, Brief), then **mints the design
on-chain (Utility NFT)** and shares/sells it via the community feed and
marketplace. The deepest module is an **EasyEDA-inspired schematic + PCB
editor** with a native (KiCad-less) Schematic→PCB pipeline. This is a **real
product, not a prototype** — every control must do real, verified work.

> **Next.js is modified here.** See `@AGENTS.md`: this is Next 16.x with breaking
> changes. Read `node_modules/next/dist/docs/` before writing any Next-specific
> code.

### State / store (`store.tsx`)

- One `PcbState` object; actions built with `useMemo`.
- **`merge(patch)`** — plain state update (view/UI, no undo).
  **`mergeWithHistory(patch)`** — model changes; snapshots `SNAP_KEYS` for undo/redo (diffed, so no-ops don't pollute history).
- **`stateRef.current`** — read latest state inside async/event actions.
- **`setToolAs(tool, text)`** — arms a place tool whose object carries a given name (`state.placeText`, consumed + cleared by `placeObject`). Lets several menu rows share one symbol kind honestly: Insert ▸ Power & Ground places `vcc5v` as **VCC / +5V / -5V**, and the supply glyph draws `obj.text`.
- Actions may call `actions.<other>()` (safe — invoked on events, not during render).
- **Persistence:** the *document* (`objects, pcbBoard, twoD, threeD, gridSize, gridType, unit, snapEnabled, designRules, pcbDrcConfig, pcbLayers, pcbNets, pcbDefaults, boardSettings`) auto-saves (debounced) to `localStorage` under `ideeza:pcb:doc:<projectId>`, scoped by `ideeza:manual:active`. So layer colours/visibility/lock, net colours, place defaults, grid style and DRC rule-tuning now survive reload. UI flags (zoom, panels, menus, sheets) are session-only. `saveDoc()` force-writes; `sanitizePcbDoc()` shape-checks every key on load.

### `CanvasObject` — the universal placed-object model

`kind, x, y, endX/endY` (wires), `text, rotation, color, layer, net, footprint,
comment, side, props` (typed-field bag), `scope` (`"schematic"|"pcb"`),
`sheetId` (multi-sheet), `sourceId` (cross-probe link), `points` (real polygon
rings for Combine results). Add a field here + handle it in `placed-objects.tsx`
+ (if persisted) the doc sanitizer.

The sidebar carries *Upgrade to Builder*, a Support block (each row disabled with the reason until it has a destination) and, beside the account row, a wallet → `/history#credits` and a bell listing the builds needing attention.

- **The build page is one card driven by one state table** (`build-shell.tsx` + `build-status.tsx`, Ai-Flow 11–14) — a plain “← Back” link (back where you came from, else the source chat) over one 580 px card: the locked-concept strip (`CONCEPT n · IN BUILD` chip · title · spec line · state badge), a banner, the five artifact rows (icon · label · `ITEM_SUBTITLES` · status — *Waiting · NN% · Ready · Couldn't generate · Didn't run*, with a progress bar only while a piece is building or finished), the clock line, and a footer that ends in one link. Every string comes from `stateRowFor(job, now)`, so **queued · waiting on credits · running · partial · system failure** can't be described one way in the badge and another in the footer: a partial build names the steps that failed and the ones that are safe (`The PCB step failed` · `The PCB and Wiring steps failed`) and offers the per-row **Retry <piece>**, while a system failure says nothing ran and carries the whole-build **Try this build again** (which really restarts and re-charges the build) beside **Back to chat** — and when a piece had already landed, the failure copy names it (*only your 3D model was finished*) instead of claiming nothing was delivered. Verified in both themes over CDP (210 checks) plus a 38-case unit check of the table.
- **A queued build can be cancelled; a running one that overruns can be stopped** (Part 4 §4.6) — two different answers because the money is in two different places. **Cancel** is offered on a queued build only (`cancelBuild` in `history.tsx`, a no-op on any other status, guarded inside the updater so a status that changed between the click and the call still decides it). It promises no refund, because a queued build has never been charged: the simulator charges when a build *starts*, and the line under the control says exactly that. **Stop and refund** appears on a running build once `isOverrunning(job, now)` — past roughly twice its estimate, the spec's own threshold — and here a refund really is owed, so it marks the job a system failure and lets the simulator's existing refund effect return the credits rather than opening a second path to the ledger. The offer rides the card's own `useMinuteClock`, so no new timer. Verified over CDP: cancel removes the queued job, leaves the balance alone and returns to the chat, while a running build offers no cancel; and a job 25 minutes into a 10-minute estimate shows the offer, where one at 12 minutes does not, with the stop returning 4 credits.
- **"Review your deliverables" is where a finished build lands** (`create/review-outputs.tsx`, Ai-Flow 15 · DL-02 · DL-03 · Wiring · Parts) — the `BUILD READY` card carries **one pill tab per artifact the build really made** (3D model · PCB · Firmware code · Wiring · Parts, in `ITEM_LABELS` order; `?tab=<kind>` preselects one, so another surface can link straight at the parts list), the artifact itself on the left inside a 520 px scroll panel (the `ModelViewer` with its generating state, else the previews derived from the build's own parts) and a **WHAT THIS COVERS** card beside it reading `WHAT_SHIPS[kind]` — it describes what the build covers, since the surface offers no download and the old heading named file formats (Gerber bundle · STL + STEP · BOM CSV) nothing here hands over —, with `PartsSummary` above it on the Parts tab. Its footer is the only decision: **Save Project** opens **the build's own Brief** (`/build/<id>/brief`) — the flow the design draws, where the build is *given* a project rather than silently made one — and **Advance Edit** skips it, making (or reusing) the project through **`projectFromBuild`** + **`setBuildProject`** and opening it at `/project/<slug>/pcb`. **One project per build**: `projectFromBuild` names and describes it in the build's own words, records `buildId`, and hands the same one back on a second press, a second visit, or two presses inside one tick (the store keeps a by-build ref, since React state hasn't flushed yet inside that tick). **Save Project creates nothing on its own** — it used to `projectFromBuild` + push `/projects`, so the Brief was never entered, the maker never chose a project, and the create silently switched which project every editor route was working on (only on the first press, which made the two presses behave differently). **Once the build carries a project the footer says so** — *Saved to `<name>`. Pick the brief back up, or open the project to keep editing.* over **Continue Brief** (back into `/build/<id>/brief`, which by then runs on the project's own draft) and **Open Project** — instead of repeating the two first-time buttons as if nothing had happened; a stored `projectId` whose project is gone reads as unsaved. A build with nothing to review keeps the teaching empty state instead of empty tabs. **Saving is what ends the review** — `buildAttention` reads a build's `projectId` as "already taken somewhere", so the sidebar bell and the ready toast go quiet the moment Save Project or Advance Edit makes the project; the review reason used to clear only on an `outcome`, which nothing sets since the picker was removed, so a saved build asked to be reviewed forever (verified: bell `1 needs attention` → `No notifications yet`, still quiet after a reload). *(Removed with the redesign: the Private/Community/Sell outcome picker and its dialog, the per-kind "What is this?" blurb and the Download .glb link — minting and outcomes are the Brief module's step; `/api/projects` is untouched, and the store's `setBuildOutcome` / `BuildOutcome` went with the picker, since nothing set an outcome any more.)* Also fixed here: a build-status row that reached **Ready** before a later system failure keeps its success tone — greying it denied work that really was produced.
- **The ready/retry/credits toast is top-centre, one shape, three tones** (`create/attention-banner.tsx`, Ai-Flow 20) — a `role="status"` card fixed `top-[16px]`, centred (`left-1/2 -translate-x-1/2`, 540 px), reading `topAttention` off the same history store the sidebar bell and build page read: **review** (brand icon tile, `BUILD READY TO REVIEW`, `<title> is ready`, **Open build**) · **retry** (warning tile, `BUILD NEEDS A RETRY`, `<title> · the <failed steps> step failed`, **Open build**) · **credits** (warning tile, `BUILD PAUSED`, `<title> is paused — top up credits to start it`, **Top up credits** → `/history#credits`) — the credits branch used to fall through into the review styling with no copy of its own. The enter transition is 150–250 ms and static under `prefers-reduced-motion`; × calls `dismissAttention` (the sidebar's red dot stays on independently). Auto-hides on the build's own page.
- **A prompt can describe a system, not just an object** (Part 4 §4.4, `lib/create/companions.ts` + `api/concept/companions` + `create/companion-picker.tsx`) — accepting a concept asks whether this product needs other *products* to work (a drone needs a remote, an earbud a charging case), and the answer fills a **Products in this build** section that **leads** the Generate gate — it decides how many deliverables there are (five per product), so it reads before the manifest that lists them. One dialog, not a screen in front of another one asking the user to approve the same build twice. The concept the chat started from is the **first row** rather than a separate card above it, so there is one list and one place to look. Classification is automatic, and it answers in two steps. The model first, since only it can reason about a product nothing has heard of; when it cannot answer, a **deterministic rule** does (`classifyByRule` in `lib/create/companions.ts`) — a small hand-written table of the families where a companion really is a separate product: a drone is flown with a controller, earbuds live in a case, a sensor node reports to a base station. The rule exists because the text provider stopped serving and every build then took the silent path, so the feature read as *"your product needs nothing"* when in truth nothing had run — silence that looks like an answer is its own kind of lie. It **cannot invent**: every companion it offers is written in that table by hand, and anything outside it is a single product, which remains the honest default and the common case. Verified against nine prompts: the drone, earbuds, sensor node, smart lock, fitness band and robot vacuum are systems; the bedside lamp, kitchen timer and bicycle speedometer are not. *(Plurals are spelled out on every head noun — `\bearbud\b` does not match "earbuds", and a missing `s?` silently drops a whole family with no error anywhere.)* **AI Horde text was measured and rejected for this**: its JSON was perfect (6/6, ~7 s) but its judgement was not — every one of six prompts came back `isSystem: true`, including a kitchen timer needing a "Remote control" and a speedometer needing "Speedometer, Speedometer, Speedometer". Most concepts are one object and never see the screen (verified: a drone returns a remote and a charger, a desk lamp returns nothing). The list is **AI-generated and read-only**; the original concept is always included and has no control beside it; selection blocks nothing. A ticked row's **Generate concept** runs **in the dialog**: it stays open, the row shows the render's own progress as a percentage and a bar, and the preview lands in place. Every row carries a small preview, and clicking one opens it larger inside the row with **Refine** (describe a change) and **Regenerate** beside it — §4.4.5's "behaves exactly like the primary concept loop", without sending the user back to the thread and asking them to return. The prompt inherits the parent's own words, so the products read as a family. The primary's row is preview-only: it was approved by pressing Use this concept, and its own refine and regenerate live on its card in the chat. The **estimate is live** and counts only what still has to be rendered, because §4.8 says deselecting keeps the concept — re-selecting must not charge twice. **§4.4.3's escape hatch is real**: the gate always carries a field to name a product the classifier did not offer (*Single-product build — name a companion product…* when it found none), and the row it adds is plainly the user's own, so a classifier miss is never a dead end. The cost chip follows the selection — `Uses 4 credits` becomes `Uses ~5 credits` the moment a companion needing a concept is ticked.
- **"Use this concept" says it is working** — pressing it runs two model round-trips (read the concept back, then classify it) before the gate can open, which is seconds of nothing. The button becomes a disabled, `aria-busy` **Preparing…** with a spinner for exactly that window, on the card that was pressed.
- **A build carries every product, not just the first** (`BuildJob.companions`, `productsOf`, `allItems`) — §4.4.8 puts all products in one project, so they are one job. Each product has its own five artifacts, its own concept and its own parts, and every rollup reads the whole job: a build whose drone is finished while its remote still renders is **running**, not ready, and the shell keeps showing the status card until all of them land. The build page groups the rows under each product's name, the review surface grows a **product switcher**, and each product's deliverables are derived from its own parts (verified: the drone's BOM lists Drone MCU, the remote's lists Remote MCU). A per-artifact retry, a whole-build retry and a system failure all address the right product. Failure copy names the product too, since "the PCB step failed" would not say whose.
- **Every product carries a confidence badge** (§4.3, `lib/create/confidence.ts` + `create/confidence-badge.tsx`) — output is **always delivered**; the badge says what checking it passed. Two tiers, `Checked` and `Draft`; **`Verified` is deliberately not rendered**, because the spec says an unreachable top tier only tells users something is being withheld. A `Draft` badge opens the grouped issue list (§4.3.5: design rule · assembly · works-with), and each row says whether a check **ran and found something** or **could not run at all** — different things, so they do not read the same. **Today every product is `Draft`**, and honestly so: a build produces a parts list, a net graph and board dimensions but no copper, so `runDrc` has no geometry to measure and the row says exactly that instead of implying a fault the user could fix. What *is* really checked is **§4.4.10's cross-product compatibility**, which needs no geometry — radio protocol and charging connector are read from each product's parts, a mismatch is reported in plain words, and it lands in **both** products' lists. The project's headline state is the lowest tier of any product (§4.4.9). The `Draft` refund sentence (§4.3.4) sits inside the list, where someone reading their issues will see it.
- **Credits are a real ledger** (`lib/create/credits.tsx` + `create/credits-card.tsx`) — a full build costs `BUILD_COST` (4) credits and every concept render costs `CONCEPT_COST` (1) — the first draft, a refine and a regenerate alike. Charging refines alone would have left the loophole open, since regenerate runs the same model for the same money. A render is charged inside `runGeneration`, the single funnel all three entry points go through, keyed by the turn it will land in; a render that never arrives is **refunded**, the concept counterpart of the build's system-failure rule. Every control that starts one — the home composer's send, the chat composer's send, Refine, Regenerate, the concept image itself and a failed card's *Try again* — is greyed with the reason when the balance cannot cover it. Charge and refund are keyed by build id and idempotent (a build can only be charged once while that charge is open, and re-charged after a refund), the balance and every entry persist to `localStorage`, and the Credits card lists the ledger in words. There is no payment integration, so the free top-up says so plainly.
- **A build is five artifacts, one worker and two honest failures** (`lib/create/history.tsx`, `create/build-simulator.tsx`, `lib/create/build-artifacts.ts`) — `startBuild` books every job with the same five items; a second build comes back **queued** and the simulator promotes the oldest queued job the tick after the worker frees up, charging the credits when it really starts (and parking it back in the queue, `blocked: "credits"`, when the balance can't cover it). A **system failure** fails the whole job and refunds; retry restarts and is charged again. A **per-artifact retry obeys the same one-at-a-time rule**: if another build holds the worker the retry waits in the queue and keeps the artifacts it already delivered, and the queue copy names the real number of builds ahead rather than assuming one. *Honest limit: nothing in the app decides to fail — there is no random injection, so in a production build the failure states (whole-build system failure and a per-artifact “Couldn't generate”) are unreachable except from a draft that already carries one. They are driven for development and verification by `__ideezaFailBuild` / `__ideezaFailItem`, which `build-simulator.tsx` installs only when `NODE_ENV !== "production"`.* The simulator is mounted once beside the providers, so builds keep advancing while the user reads their chat. Each artifact's content (BOM, netlist, firmware sketch, board size) is derived from the concept's parts, deterministically.
- Background **video/render jobs** (`components/video-jobs`, global render indicator).
- **A concept turn has three states, each drawn for what it is** (`image-turn.tsx`, Figma Ai-Flow 02–08): **rendering** is a bare 640×530 tile — no card chrome — with a brand-tinted border, a dotted texture and one centred pill naming the concept and its live progress (`Rendering concept 2 · 41%`); **failed** is a card with a triangle in a red-subtle circle, *"Couldn't draft that concept"* and **the reason it failed**, because the three reasons need different instructions: the image service **refused the render for want of credit** (*"Trying again won't help until it's topped up"* — a retry loop has one answer and saying "try again" there wastes the user's time), it was **busy and didn't finish in time**, or **the user's own balance ran out** before the render started. An older turn carrying no reason keeps the generic line. The image is stored under the bare id and its `{prompt, seed}` sidecar under `<id>.json`, both derivable from the id alone — and the derived URL is checked against the one the API returns on every write, so a change in the URL shape fails loudly at the write rather than quietly 404ing at every later read. **The disk driver is why image generation broke on the live site**: a serverless filesystem is read-only apart from `/tmp`, so `put` threw `EACCES`; `/tmp` would not have saved it either, since the next request can land on another instance. ### Schematic connectivity, ERC, netlist & annotation (`nets.ts`)
- **Live netlist** — symbol kinds carry pin anchors (`SCHEM_PINS`); `computeNets()` union-finds pins + wire endpoints into nets, named from net-label / power / port symbols (same name merges) else auto `N1…`. Pure/derived — always reflects the drawing.
- **Auto-junction** — a wire ending on another wire's **interior (a T)** is electrically joined (on-segment union) and a **junction dot** is auto-dropped there on wire-finish.
- **Buses are bundles, not conductors** — a bus carries a `PREFIX[lo:hi]` name and **expands to member nets**: `computeNets` excludes buses from the electrical graph, so branch wires connect by member label (`BUS_D3` here = `BUS_D3` there, via same-name merge) and each member is its own net in the netlist. Bus membership (for ERC) is geometric (a pin/branch endpoint on the bus line).
- **Nets tab** (navigator) lists the live nets with object counts; clicking highlights the net (members via connectivity → `highlightedMembers`, since schematic objects have no stored `net`).
- **ERC** (`runErc` + `ERC_RULES` catalog) — a real rule engine over the live connectivity, emitting findings on the EasyEDA-Pro **5-level severity scale** (Note · Warning · Error · **Fatal**). Enforced rules: floating pins, free/dangling wire, single-connection net, label-not-connected, duplicate & unannotated & mis-formatted designators, empty Value, netflag/netport-needs-name, illegal net name (charset/length), illegal bus name, multiple-net-names-on-one-net, global-net short, port/flag/off-page name-vs-wire mismatch, unpaired differential pair, overlapping-unconnected pins (bare pin tips with no wire/junction join), **bus rules** (illegal bus name, bus-branch member naming `PREFIX[lo:hi]`, and netport/netflag/off-page ↔ bus name-match — a bus bundle legitimately carries many member names, so multiple-net-names is suppressed on it), and the **pin-conflict matrix** (Connection tab). Severities live in one catalog (`ERC_RULES`). The pin-conflict rule reads each pin's electrical type (`SCHEM_PIN_TYPES` / `POWER_PIN_TYPE` / `props.pinType`) and looks up the pair in `defaultPinMatrix()` — so two op-amp outputs = Error, Power↔Ground/OUT↔Power = Fatal, while normal passive nets stay clean (matrix default is Ignore; a No-Connect flag suppresses the net). Results show in the bottom **DRC/ERC tab** (Fatal/Errors/Warnings/Notes counts) via "Electrical Rule Check" / Design ▸ Run design check, **and on the canvas** (UIUX-81, `drc-markers.tsx`): each finding names the objects it is about (`ErcIssue.ids`, filled by `emit`), so the offending wire · pin · part · flag is **ringed where it sits** — a dashed circle sized to that element's real bounds and coloured by severity (Fatal · Error · Warning · Note), with the severity dot and its tooltip on the ring. A finding that names nothing keeps the small positional marker, and the bottom tab's **Show on canvas** turns the layer off. Verified against a sheet built to trip one rule per severity: overlapping pins (Fatal), an unnamed Netflag (Error), GND shorted to VCC (Warning) and an unannotated `R?` (Note) — 8 dashed rings, four distinct severity colours, and the shorted wire's ring 232 px wide against a symbol's 32. **Config-driven** — `runErc(objects, cfg)` reads the **Design Rules dialog** config (`state.designRules`, persisted per-project in the doc): a disabled rule is skipped, a re-severitied rule reports at the tuned level, and the pin-conflict matrix + its master toggle come from the config. The dialog (Save → `setDesignRules`) is the real tuning surface, not a stub. **Its shell is IDEEZA's own** (UIUX-39, titled **Electrical rules** — the term the Design menu and the toolbar's ERC control already use; “Design Rules” pointed at the board's dialog): a category rail (Nets & connectivity · Components · **Agile Modules** · Pin conflicts) with per-category *on / total · checked* counts, a whole-config summary (`23 of 35 rules on` + severity chips), a rule filter, an **Only rules the engine checks** toggle and Enable/Disable-shown. **A rule row is one decision, not two controls** — it used to carry EasyEDA's anatomy (a checkbox, a `01`/`02` number, the rule text, a severity badge on the right), where "on" and "how loudly" were separate switches that could contradict each other. The number and the checkbox are gone; the row is the rule text over a state line in words (*Reported as a warning* · *Not reported* · *Not checked yet*) with one **five-stop report level** on the right — **Off · Note · Warn · Error · Fatal** — so the current level and every alternative are visible at once instead of hidden behind a dropdown. `Off` writes `enabled:false` and a level writes `enabled:true` + that severity, so the engine's model is untouched (a stored `Ignore` severity reads as Off rather than leaving the control blank). Rules the engine doesn't implement yet carry a **“not checked yet”** badge (from `ERC_ENFORCED_ROWS`/`ERC_RULE_AT`, exported from `nets.ts` as the inverse of `ERC_TO_DIALOG`) so a toggle never pretends to matter. **The config contract is load-bearing** — `runErc` looks rules up by category + row index, so the dialog never reorders or filters the stored arrays; the search box filters only what is displayed and every row keeps its true index. **Every toggle is keyboard-operable** — the rule rows, the *Only rules the engine checks* filter and the pin-conflict master were `<span onClick>` around a painted box, so Tab never reached the controls that decide what the checker reports; they are `<button role="checkbox" aria-checked>` now (`CheckRow`), and the design-system `Checkbox` gained a `decorative` flag so the painted box inside a labelled control no longer announces a second, nested checkbox role (verified: 0 nested roles). **The footer carries the decision alone** — Cancel (discards the buffer) · **Save & check now** (saves, then really runs `runErcCheck` and opens the results tab — the old “Verify Now” only switched tabs) · Save. ### Interactive routing — corner style + obstacle policy (`route-path.ts`)
`planTrackPath(state, from, to)` decides the polyline a drafted track really takes, and the **draft preview and the commit call the same planner**, so the dashed path is what lands. **Routing Corner is two choices, not one list** (UIUX-91, `CORNER_STYLES`) — the **shape** of the bend (a straight miter or a rounded arc) and the **angle** its legs are held to (45° · 90° · free) — so the menu carries the six combinations in two groups: **Line 45° · Line 90° · Line Free Angle │ Arc 45° · Arc 90° · Arc Free Angle** (the old flat *Any angle / 45° / 90°* conflated the two and had no arc at all; stored ids migrate on load). ### Boolean / Combine geometry (`shape-boolean.ts`)
Union · Intersect · Difference · XOR on shapes/copper-regions — each shape → polygon, rasterised, combined per-op, traced with marching-squares → a real filled `points` polygon (holes via even-odd fill).

The trim is clamped to half of each adjacent edge so an oversized value can't fold the shape inside out, collinear vertices are skipped, and the toast reports the clamping (`Chamfered 1 shape · 4 corners clamped to fit`). Eligibility is `isCombinable` — the same shapes Combine accepts — and the dialog states it live (`Will apply to 1 shape`), with Apply disabled when nothing qualifies. ## 6. Coding conventions

- **Workflow — use the superpowers skills for code work.** Start any coding task by invoking **`/using-superpowers`**; follow its process flow — **brainstorming** before building a feature, **writing-plans** for multi-step work, **test-driven-development** while implementing, **systematic-debugging** for any bug, and **verification-before-completion** before claiming done. Don't jump straight to editing.
- **Real logic, never stubs.** No button that only `flashToast`s or sets a dead flag. Implement the actual behaviour (correct math — group rotate/flip pivots on the selection centroid; z-order reorders the objects array), then **verify in a real browser**. Be upfront about anything still incomplete.
- **`tsc --noEmit` must pass.** `data.tsx` is `@ts-nocheck` (pure data builders) — everything else is type-checked.
- **Store discipline:** pick `merge` vs `mergeWithHistory` deliberately (model change → history). Read via `stateRef.current` in event/async actions. New persisted state → add to the doc type + sanitizer + save effect.
- **One model:** route new placed things through `CanvasObject` + `placed-objects.tsx` rather than bespoke rendering.
- **Match the surrounding code** — comment density, naming, idiom. Reference files as `path:line`.
- Prefer editing the existing builders (`data.tsx`, `inspector-schema.ts`) over parallel systems.

## 7. UI/UX guidelines

- **Workflow — use `/ui-ux-pro-max` and `/impeccable` for UI/UX work.** Plan and build any interface, visual, layout or design-system change through these skills (they enforce the register, tokens and craft rules below). Reach for them on new surfaces, redesigns, polish passes, and design critiques.
- **An opacity modifier does not work on a token colour.** Tailwind v3 can only inject alpha into a colour it can parse, and every DS colour is a bare `var(--color-…)`, so `bg-bg-page/60` compiles to **nothing at all** — no rule, no error, an invisible element. Four modal scrims and a destructive chip's hover were written that way and painted nothing. Reach for `bg-[color-mix(in_srgb,var(--color-bg-overlay)_62%,transparent)]`, or a token that already means what you want (a dialog's footer band is `bg-bg-subtle`, not the page colour at 40%). The same trap catches a colour key that does not exist: the preset's border colour is `DEFAULT`, so `bg-border-default` is also nothing — it is `bg-border`. Both are invisible in review and in the browser; grep the compiled sheet if you are unsure a utility exists.
- **Tokens only** — never hardcode color/spacing/radius/shadow/type. Use `--color-*`, `--spacing-*`, `--radius-*`, `--font-size-*`, **`--line-height-*`**, **`--letter-spacing-*`**, `--elevation-*`, `--border-width-*`. Both **light + dark** themes (`data-theme` + `prefers-color-scheme`).
- **Line height pairs with font size** — `text-md` wants `leading-md`; `leading-relaxed` is the multi-line prose variant for any size. (The Figma collection offsets the two scales — `line/height/5xl` sits with `font/size/4xl` — so the pairing is made explicit in `tokens.css`.) Letter spacing: `tracking-tight` for display type, `tracking-wide` for label type, **`tracking-caps`** for the uppercase micro-labels the panels are full of. An arbitrary `leading-[19px]` / `tracking-[0.5px]` is now a token violation.
- **A pad is copper, not a layer** — `--color-pad-copper` / `--color-pad-mechanical` are the material colours a land pattern reads in (the footprint editor, its previews and the 3D placement all share them). `--color-pcb-top-copper` is red because the *board* locks Top = red; that identity says nothing on a single part.
- **`text-tertiary` is a reading colour, not a whisper** — it labels half the panels in this app, so it has to clear 4.5:1 on the surface behind it. Light was `gray-400` (**2.34–2.56:1**, a real WCAG 1.4.3 failure wherever it carried words) and is now `gray-600`; `text-disabled` steps down to `gray-400` and `icon-secondary` to `gray-500` so the three stay distinguishable, and dark mirrors the same order. Disabled text is deliberately left below 4.5:1 — WCAG exempts inactive controls, and lifting it would stop it reading as disabled.
- **`Segmented` vs `ButtonGroup`** — `ButtonGroup` announces `role="tablist"`: right for switching *which view you are looking at*, wrong for choosing a value, because a screen reader then calls the options tabs. Use **`Segmented`** (`role="radiogroup"`) when the choice *is* the data — a unit, an angle, a mode.
- **Weight matches urgency** — `Banner`'s `attention` tone blocks Next, so it keeps a filled, bordered box; `good` is the *absence* of a problem, and a full-width saturated slab announcing that nothing is wrong competed with the step heading (in dark it was green-900 behind a green-400 edge). It keeps the tick and the success colour and gives up the fill and the border. Same rule on a chosen radio card: the border and the mark already say which one is on, so the card no longer fills with brand.
- **A card does not go inside a card** — `/parts` had bordered item cards sitting in a bordered, filled panel, which is depth for its own sake. The controls keep their grouping with a hairline under them and the cards sit on the page. (Splitting the search row from the filter row also stranded the two filters in an empty strip once the panel stopped being a card; search, filters and the visibility tabs are one band now.)
- **10px is for a micro-label, not for reading** — `--font-size-2xs` is the scale's smallest step and it had spread to card facts, hints, notes, status chips, the editor toolbars and the step rail. Navigation and anything with sentences moved up: prose and meta to `sm` (12px), uppercase micro-labels and control labels to `xs` (11px). `/parts` went from 48 elements at 10px to none.
- **Prose gets a measure** — body copy is capped at `62ch` (measured at ~74 characters a line with the real typeface, inside the 65–75 band). Before this the step headings ran 640–660px of 14px type, and a note on the part page ran the full 900px at 10px.
- **The em-dash was doing a full stop's job** — the flow's copy leaned on it in almost every sentence, which is a recognisable machine-writing tell. Rewritten as sentences where it joined two thoughts. Kept: the `Label — state` tooltip shape and the `—` empty-value placeholder, both compact conventions rather than prose.
- **`Segmented` never stretches** — it is `inline-flex`, but as a child of a column flex container `align-items: stretch` still pulled a two-option unit picker to 715px. `w-fit self-start` lives in the atom, so no call site has to remember.
- **A unit adornment is a unit, not a button** — `TextInput`'s `suffix` had a divider and a filled background, so every dimension field ended in something that looked pressable and three stacked read as a column of controls. It is quiet text inside the field now.
- **Brand = violet** (`--color-violet-600`, #7c2db9). Accent is for **selection / active / primary only** — not decoration. Restrained palette (product register).
- **The design-system `Checkbox` / `Radio` are real controls** (`components/ideeza/checkbox.tsx`) — they announce `role="checkbox"` / `role="radio"`, so they now also take focus (`tabIndex`) and activate on **Space/Enter** whenever they carry an `onChange`; they were mouse-only, which made every labelled row built on them (Sheet Border, Sheet Info fields, Zone reference, dialog toggles) unreachable from the keyboard. A `decorative` flag drops the role for the cases where the box is only the picture inside a labelled `<button role="checkbox">`, so no control announces itself twice.
- **The design-system `Select` escapes its scroll container** (`components/ideeza/select.tsx`) — the options panel portals to `<body>` with `position: fixed`, measured off the trigger, flipped above it when the rows don't fit below, clamped into the viewport and capped at 280 px with its own scroll; an ancestor scroll or a resize closes it, since the anchor it was measured against has moved. It lives inside the package flow's `overflow-x-auto` tables and the PCB settings' scroll panes, where the absolutely positioned panel was cut to a sliver. Verified over CDP: portalled to `<body>`, flipped above a trigger 40 px off the viewport floor, wholly on screen, commit by click and by ArrowDown/Enter, Escape and an ancestor scroll both close it.
- **`Segmented` keeps the radio-group contract it announces** (`components/ideeza/segmented.tsx`) — it called itself a `radiogroup` while every option was a Tab stop and the arrows did nothing. It is one Tab stop now (roving tabindex on the chosen option), Arrow Left/Right/Up/Down move the choice and wrap, Home/End jump to the ends, and selection follows focus. The chosen option paints **brand-subtle fill + brand text**, the treatment `ButtonGroup` and the PCB right panel already use, instead of a solid brand slab that spent the accent on a control that is not the page's primary action.
- **One `Banner`, four tones** (`components/ideeza/banner.tsx`) — `good` · `attention` · `info` · `error`, with an optional `title` that puts the tone in the glyph and the page's own ink in the words. The build page used to carry a second banner with its own tone table and its own padding; `build-status.tsx` maps its state names onto the atom's tones, so the queue, the partial failure and the system failure all come from one control.
- **The design-system `Select` is a real listbox** (`components/ideeza/select.tsx`) — the trigger announces `combobox` and the panel a `listbox` of `option`s, ArrowDown/Up walk the options (wrapping), Home/End jump to the ends, Enter/Space commit, Escape closes and returns focus to the trigger, and Tab closes it on the way out; the active option is named by `aria-activedescendant`, so focus never leaves the trigger. The options used to be `<div onClick>` with no role and no key handling, which made **every filter and form field built on this component mouse-only**. Hover and the keyboard share one highlight, so arrowing looks like pointing.
- **A symbol kind with no glyph is a defect, not a fallback** — `GLYPHS` had no `ic`, `connector` or `transistor`, so `glyphFor` returned its generic dot: placing an ESP32, a USB-C connector or a MOSFET from the catalogue drew a **black circle on the sheet**, and 8 of the 15 catalogue rows previewed as one. All three are drawn now, in the same register as the rest (centred on 0,0, `currentColor`, ~1.6 stroke): an IC body with its pins and pin-1 mark, a connector shell with its contacts, and a BJT with the emitter arrow. The geometry itself moved to **`lib/pcb/glyphs.tsx`** so a surface that only wants to *draw* a symbol can import it without pulling in the editor's store; `placed-objects.tsx` re-exports it, so the canvas is unchanged.
- **Shared classes** (`pcb-editor.css`): `.ix-tool` (icon button), `.ix-row` / `.ix-mi` (list/menu row), `.ix-menu` / `.ix-submenu`, `.ix-tab`, `.ix-pill`, `.ix-btn`, `.ix-seg`. Reuse them; don't reinvent hover/active states.
- **Icons:** `<DsIcon name={...} size strokeWidth />` — resolves a Hugeicon first, falls back to the SVG-string dictionary.
- **Menus & dropdowns must never clip.** The editor is full of scroll/overflow containers → any flyout **portals to `<body>` with `position: fixed`** and **clamps into the viewport** (flip left near the right edge, shift up near the bottom). Anchor context menus at the cursor.
- **Earned familiarity** — behave like Figma / EasyEDA / KiCad / Linear; the tool disappears into the task. No invented affordances for standard actions.
- **Contextual disable, not stubs** — grey a control when its precondition isn't met (Copy needs a selection, Cross Probe needs a PCB link); light it up when it is. **Empty states teach** ("No nets yet — convert to PCB to generate").
- Motion 150–250 ms, ease-out; state feedback only, no decorative choreography.
- The Position/arrange panel is the reference for dense control layout: equal-size boxes on an aligned grid, segmented icon groups with hairline dividers.

## 8. Scope / direction


Building a **real, shippable product** in phases (schematic → PCB → routing/DRC →
manufacturing/export). The Schematic→PCB engine is **native in-app** (KiCad
export exists via `kicad-export.ts`, but conversion/placement/routing are our
own). Communicate concisely; keep changes tightly scoped to what's asked.
